## 摘要

### 项目目的

本项目以具体的 Agent 结构化信息处理场景作为验证载体，但不以训练单一业务的专用模型为最终目的，而是探索一套可迁移、可复用的本地小模型解决方案。

项目目的分为“实验与效果验证”和“项目通用性与面试展示”两个层面。

**实验与效果目标**

1. **验证本地模型替代远端 API 的可行性**：将 Agent 中高频、规则明确的大模型调用迁移到本地，使用能够在普通个人电脑 CPU 上运行的小参数模型完成任务。
2. **验证成本、延迟与任务质量的改善效果**：减少远端 API 费用和网络依赖，降低响应延迟，并通过领域后训练提高结构化输出、信息抽取、多轮状态理解和工具调用的准确性与稳定性。

**项目通用性与面试目标**

3. **形成可嵌入现有 Agent 的通用能力模块**：项目不绑定某个具体业务，而是沉淀一套可复用的任务定义、数据构造、后训练、评测、量化和本地推理方案。迁移到其他 Agent 场景时，可以保留整体技术框架，仅替换字段合同、工具定义、场景数据和评分规则。
4. **完整展示岗位相关技术能力**：通过可复现的实验和工程实现，系统展示模型测评、SFT、DPO、LoRA 微调、模型量化、CPU 推理、推理加速和 Agent 集成能力，为相关岗位的简历表述、项目讲解和面试深挖提供依据。

### 主要结论

1. **本地替代具有可行性**：经过领域数据监督微调后，小参数模型在格式遵循、字段抽取、多轮状态理解和工具调用判断方面明显优于原始基座模型，能够承接边界清晰的结构化任务。
2. **质量与性能需要分别优化**：后训练主要解决任务准确性和稳定性问题；本地推理优化主要解决 CPU 运行速度和响应延迟问题，量化、缓存和运行参数调优都是实现这一目标的手段。
3. **Prefill 是主要性能瓶颈**：较长系统提示词带来的 Prefill 占据主要推理时间，公共前缀 Prompt Cache 可以显著降低缓存命中请求的首字延迟。
4. **工程可靠性需要分层保障**：模型负责语义理解，工具提供外部事实，代码执行确定性规则与协议校验，以降低模型幻觉和不稳定输出对业务流程的影响。

### 技术栈

- **本地模型对比与测评**：Qwen3-0.6B、Qwen3-1.7B、Qwen3-4B、JSON Schema、Pydantic、自定义评分器、sentence-transformers。
- **后训练**：SFT、DPO、PyTorch、Transformers、PEFT、LoRA、LLaMA-Factory。
- **模型推理**：llama.cpp、GGUF、CPU 参数调优、Prompt Cache，以及 Prefill、Decode、TTFT 和吞吐测量。
- **推理性能优化**：模型量化、CPU 参数调优、Prompt 压缩和公共前缀缓存，以及各项手段对首字延迟、生成速度、资源占用和任务质量的影响。

## 第一部分：项目技术报告

### 1. 项目目标

本项目希望将 Agent 中高频、规则明确、输出边界清晰的远端大模型 API 调用，替换为能够在普通个人电脑 CPU 上运行的本地小参数模型。

本地部署可以减少按次调用费用和外部网络依赖，使敏感数据尽量保留在本地，并提高系统的可控性和可离线运行能力。但本地小模型也面临两个直接问题：一是参数规模较小，未经专项训练时任务准确性和格式稳定性不足；二是普通 CPU 算力有限，模型体积、首字延迟和整体推理速度可能无法满足实际使用要求。

因此，项目按照两个前后衔接的阶段推进：

1. **阶段一——后训练提升质量**：通过任务数据构造、SFT、DPO 对照实验和错误驱动迭代，提高本地小模型的任务准确性、格式遵循能力和输出稳定性，并选出满足质量要求的模型。
2. **阶段二——本地推理性能优化**：在阶段一选定模型的基础上，先结合推理阶段和硬件特征定位性能瓶颈，再综合使用模型量化、CPU 参数调优、Prompt 压缩和公共前缀缓存等手段降低首字延迟与端到端时延，同时评估每项优化带来的质量代价。

项目最终关注的不是单一实验指标，而是在任务质量、模型体积、推理速度和部署成本之间取得可落地的平衡。

### 2. 总体技术方案

项目从本地基座模型对比开始，先建立训练前质量与性能基线；随后进行后训练并选出质量达标的模型；再对该模型进行合并、量化和 CPU 推理优化；最后将优化后的模型接入 Agent 应用进行验证。

### 3. 阶段一：后训练提升任务质量

#### 3.1 阶段目标

阶段一的目标不是提高模型的通用对话能力，而是让本地小模型掌握 Agent 场景中的确定任务合同：从单轮或多轮对话中提取状态，根据缺失字段和工具结果选择下一步动作，生成合法的工具调用或结构化 Final，并保证回复与结构化字段一致。

初始基模虽然能够理解用户的大致意图，但在严格业务任务中存在明显不足：Qwen3-0.6B 在最初 51 条评测中仅通过 2 条，协议遵循率为 39.2%，任务正确性均分为 37.7%。主要错误包括 JSON 或 Schema 不合法、字段丢失、旧状态错误继承、缺少必要信息时提前调用工具、工具参数错误，以及工具结果与最终回复不一致。因此，本阶段使用后训练重点解决四类问题：

1. **协议稳定性**：稳定输出符合合同的 JSON、字段和枚举值；
2. **状态理解**：正确处理多轮继承、局部修改和旧工具结果失效；
3. **动作判断**：在追问、工具调用、结果确认、拒绝和转交之间选择正确动作；
4. **业务正确性**：准确提取时间、时长、技师和偏好，并保证工具参数、状态和回复一致。

#### 3.2 面向 Agent 业务场景的评测

项目没有使用通用知识问答或文本生成榜单评价模型，而是围绕真实 Agent 执行链路设计并构建了 **75 条任务级评测样本**。评测集覆盖信息缺失追问、字段提取、工具调用、工具结果处理、多轮状态修改、用户确认或拒绝以及无关输入等完整业务链路，同时包含单轮与多轮、Final 与 Tool Call、正常路径与边界异常等不同类型。

评测以“是否能够被 Agent 系统正确执行”为标准，而不是只比较答案文本相似度。评分包括两层：首先检查输出是否为合法 JSON、字段是否完整、枚举和工具协议是否符合 Schema；随后检查动作、字段、工具名、工具参数和自然语言回复是否符合业务预期。只有协议通过且任务正确性不低于 0.95，才计为有效通过。大部分指标由确定性规则计算；只有偏好类自然语言使用本地中文 Embedding 辅助匹配，不依赖远端 LLM-as-a-judge。

75 条样本分为两部分：51 条主评测集用于回归测试和错误定位，其中包含 36 条结构化 Final 和 15 条 Tool Call；在发现主集已被多轮用于分析和数据迭代后，项目又额外构建并在训练前冻结了 24 条独立 holdout，用于检验未见表达下的泛化能力。最终候选 0.6B SFT 在主集通过 40/51，在 holdout 通过 21/24，合计通过 **61/75**。这说明提升并非只来自记忆固定样本，但当前评测规模仍然有限，结论只代表已覆盖的业务边界。

#### 3.3 SFT：从基础能力建立到错误驱动迭代

项目采用 LoRA SFT，让小模型学习业务协议、状态更新和动作决策。本节不按训练轮次罗列过程，而是围绕四个问题展开：**如何改数据并重新训练、如何处理质量回归、如何选择数据并判断补充数据的收益，以及下一步如何继续提升。**

##### 3.3.1 如何修改训练数据，通过重新训练提升模型能力？

**本段要讲清楚：如何将评测中暴露的能力缺口，转化为有针对性的训练样本，形成“错误归因—数据修改—重新训练—效果验证”的闭环。核心方法是 Contrast Sets（对比集）数据增强。**

初始 SFT 先通过覆盖基本业务流程的监督样本，建立协议输出、字段提取和动作选择等基础能力。后续迭代不再盲目扩充数据，而是先区分评测失败来自模型错误、数据标签错误、评分器误判还是推理配置问题；只有确认属于模型能力缺口，才进入训练数据修改环节。

**技术一：Contrast Sets（对比集）数据增强。** 对于已确认的模型错误，项目不直接复制失败的评测样本，而是抽象出模型没有学清的局部决策边界，保持大部分上下文不变，只修改一个会改变正确答案的关键条件，构造新的训练样本。例如：

- **追问与工具调用的边界**：围绕同一预约场景，分别构造“缺时间”“缺时长”和“信息完整”，使正确动作分别为追问时间、追问时长和调用工具。
- **状态继承与局部修改的边界**：围绕同一历史状态，分别构造“保持方案”“只修改时间”和“只更换技师”，使模型学习只更新被用户修改的字段，而不是重写或错误继承整个状态。

这些对比样本与原有基础训练数据混合后，重新进行 LoRA SFT，再检查对应错误是否修复、其他能力是否保持。Contrast Sets 最初用于评估模型的局部决策边界，本项目借用其构造思想进行 SFT 数据增强；它改变的是训练样本的组织方式，不是引入额外的对比学习损失。其价值在于让数据明确表达“哪个条件变化时，模型决策必须随之变化”，而不只是增加同类表达的数量。

从整体训练过程看，第一版 SFT 将 0.6B 从 2/51 提升到 24/51；后续在统一评测口径下，由 29/51 提升到最终的 40/51，独立 holdout 达到 21/24。这些结果支持“基础 SFT 加定向数据迭代”的整体有效性，但不能将全部增益单独归因于 Contrast Sets；要量化该方法的独立贡献，还需要控制数据量与训练配置的消融实验。

##### 3.3.2 新一轮训练出现质量回归时，如何定位和处理？

**本段要讲清楚：重新训练后，如果模型把原来会的题做错了，如何调整数据把这部分能力修回来。**

每轮训练后，用相同的评测集和推理配置比较新旧模型，不只看总分，还要找出“原来答对、现在答错”的用例，这就是质量回归。针对这些错误，检查训练数据是否存在标签错误、某类样本过多或相关场景覆盖不足，再修正标签、调整样本比例，或补充对比集样本，同时保留原有基础训练数据。新增样本针对错误类型构造，不直接把评测题加入训练。

例如，如果增加工具调用样本后，模型在缺少时间时也直接调用工具，就检查并补充“信息完整时调用、缺少时间时追问”的对比样本。重新训练后再跑完整评测，确认工具调用能力有所提升，原有追问能力也没有退步。如果关键能力仍然退化，就先保留之前更稳的模型。

简单来说，就是：**找出退步用例 → 检查并调整训练数据 → 重新训练 → 验证新问题修好了、旧能力也保住了。**

##### 3.3.3 如何判断数据集已经够用，可以停止继续训练？

**本段要讲清楚：根据什么判断当前数据已经阶段性够用，不再继续补数据和反复训练。**

判断依据不是数据达到多少条，也不是训练 loss 足够低，而是看三点：

1. **主要任务是否已经达到当前阶段的要求**：不仅看总分，还要检查字段提取、追问、工具调用和多轮状态更新等主要场景，不能存在不可接受的关键错误。
2. **继续补数据、重新训练是否还有明显收益**：如果多轮迭代后，评测通过数不再稳定提高，甚至修好新问题又出现旧问题，就说明沿用当前方法继续训练的收益已经有限。
3. **未参与训练的独立评测表现是否达到预期**：不能只在反复分析过的题目上表现好，还需要用独立样本检查模型能否处理没见过的输入。

本项目数据由约 795 条增加到约 1200 条后，继续训练的新增收益逐渐减少，部分版本还出现旧能力退步。最终 0.6B 在主评测集通过 40/51，在独立 holdout 通过 21/24。结合这些结果，项目选择保留当前最佳模型，停止继续堆叠同类数据和反复训练，进入本地部署优化阶段。

这里的“够用”是指**足以支撑当前阶段的实验目标**，并不代表所有问题都已解决；剩余错误和后续提升方向放在下一节讨论。

##### 3.3.4 如何进一步提升训练后模型本身的能力？

**本段要讲清楚：如果希望模型回答得更准确、掌握更复杂的任务，还能从数据、训练方式和基座模型三个方面做哪些改进。以下是后续可验证的方向，不是已完成的实验成果。**

1. **提高训练数据质量与难度。** 不再简单增加同类样本，而是修正错误或冲突标签，补充当前模型仍容易出错的复杂多轮修改、条件组合和不同表达，并调整各类样本比例。也可以让更强的教师模型生成候选答案，经规则检查和人工审核后用于 SFT，帮助小模型学习更准确的处理方式。
2. **优化训练参数与训练安排。** 对比学习率、训练轮数、LoRA rank 等配置，检查当前训练是否不足或过拟合；尝试先训练基础任务，再混合基础样本与复杂样本继续训练。目标是让模型学会难题，同时减少旧能力退步，而不是单纯训练更久。
3. **尝试能力更强的基座模型。** 如果改进数据和训练方式后，复杂状态理解与推理仍没有明显提升，可以选择同规模但基础能力更强的模型，或适当增加参数规模，再用相同任务数据微调和比较。更大的模型不保证一定更好，需要通过实验确认。

是否有效，最终都要看相同评测条件下任务准确率是否提高、旧能力是否保持，并用独立测试集检查泛化。**停止当前低收益的训练迭代，不代表模型已经没有提升空间，而是下一步需要改变数据质量、训练方式或基座模型。**

综上，本节的主线是：**如何改数据提升能力、如何修复训练后的能力退步、如何判断可以阶段性停止训练，以及如何进一步提升模型本身的能力。**

**参考资料：** Gardner et al., *Evaluating Models' Local Decision Boundaries via Contrast Sets*, EMNLP 2020：<https://arxiv.org/abs/2004.02709>

#### 3.4 DPO 对照实验与进一步优化方向

**已有结果：初始 SFT 后增加 DPO，没有带来任务通过率提升。**

项目在初始 SFT 模型之上分别测试了 `β=0.1` 和 `β=0.3` 的 DPO，并在 0.6B、1.7B 两种模型规模上与各自 SFT 父模型对照：

| 模型 | SFT | DPO β=0.1 | DPO β=0.3 |
|---|---:|---:|---:|
| Qwen3-0.6B | **24/51** | 22/51 | 22/51 |
| Qwen3-1.7B | **29/51** | 29/51 | 27/51 |

0.6B 的两组 DPO 均少通过 2 条；1.7B 在 `β=0.1` 时持平，在 `β=0.3` 时少通过 2 条。因此，项目没有采用这些 DPO 模型，后续优先推进 SFT 数据迭代。需要区分的是：这些实验基于初始 SFT，而不是最终达到主集 40/51、holdout 21/24 的 0.6B SFT，尚未验证最终 SFT 上的 DPO 增益。

**理论分析：DPO 可以用于本业务，但偏好优化不自动等于任务通过率提升。**

本业务要求模型判断何时追问、何时调用工具、如何继承状态，以及如何填写日期和参数。这些行为都能构造“同一输入下，正确输出优于错误输出”的偏好对，并不要求两个答案都正确。因此，不能因为任务答案明确，就认定 DPO 不适用。

DPO 优化的是相对于参考模型的 chosen/rejected 相对概率，而评测检查的是实际生成的完整答案是否通过。即使模型降低了某个 rejected 的概率，也可能生成另一个错误答案；某个动作或字段有所改善，也不一定使整条样本达到通过标准。另一方面，初始 SFT 的基础能力仍有较大提升空间，偏好训练的效果可能受到起点能力限制。这些是解释无收益的可能机制，不是仅凭上述通过数就能确定的原因。相关原理见第二部分 1.1。

**后续方案：在标签准确、业务规则一致的前提下，如何进一步发挥 DPO 的作用？**

以下只讨论 DPO 的训练设计，不以数据一致性问题解释已有结果；这一前提也不代表对现有数据质量的认证。建议优先开展以下调整，均属于尚待验证的方案。

1. **以最终 SFT 为起点，重新建立参考模型。** 使用已经完成定向迭代的 0.6B SFT 初始化待训练模型，同时保留其冻结副本作为参考模型。目标是在已有能力上修正剩余输出倾向，而不是要求 DPO 同时承担大量基础能力学习。

2. **围绕当前模型真实错误制作更有针对性的偏好对。** 在独立开发场景中采样最终 SFT 的回答，优先选取模型确实容易生成的错误作为 rejected；chosen 则提供经审核的正确答案。尽量让两者长度、语气和无关字段接近，使主要差异落在业务判断上，避免模型只学到“更长的回答更好”等表面规律。具体可按下表构造：

   | 优化目标 | chosen | rejected |
   |---|---|---|
   | 缺信息时正确追问 | 未提供时长时追问时长 | 自行补时长并调用工具 |
   | 正确理解确认与暂停 | 根据上下文处理“知道了”，不擅自取消预约 | 将普通回应误判为暂停或取消 |
   | 多轮状态更新 | 只修改用户指定的时间，保留其他有效字段 | 修改时间时丢失技师或时长 |
   | 日期与时间理解 | 根据参考日期和用户表达生成正确时间 | 跨月日期算错，或将下午四点写为 14:00 |
   | 严格枚举遵循 | 使用当前协议允许的枚举值 | 使用模型实际生成过的非法枚举值 |

   这些样本应针对错误类型重新构造，不直接使用最终测试题。日期类还需覆盖不同参考日期、跨月边界和表达，不能只让模型记住少数日期答案。成对构造能够突出错误差异，但不会将标准 DPO 变成逐字段监督，也不保证学会完整的日期推理能力。

3. **调整偏好对覆盖与训练强度，而不只更换 β。** 增加日期、状态更新和动作边界等当前难点的有效偏好对，同时保留已掌握场景的代表性偏好对，避免只优化一种行为。以小范围验证比较 β、学习率和训练轮数，按验证任务表现选择 checkpoint。β 控制偏好优化与参考模型约束之间的权衡，不是越大就越强地纠错；已有结果也不能证明增大 β 必然造成回归。

4. **用对照实验确认 DPO 是否提供额外价值。** 从同一个最终 SFT 出发，比较“不继续训练”“用同批 chosen 继续 SFT”和“用同批 chosen/rejected 做 DPO”，采用可比的调参投入并记录训练预算。既看任务总通过率，也看目标错误是否减少、旧能力是否退步，最后用新冻结且未参与选样的测试集确认。偏好排序准确率和 DPO loss 只作为辅助指标，不能代替业务评测。

**结论：已有实验支持当前保留 SFT 部署，但不支持排除 DPO 的进一步价值。后续若继续尝试，应从“在初始 SFT 上追加偏好训练”，转向“在最终 SFT 上针对真实残余错误进行偏好优化”。只有相对原模型和同数据继续 SFT 都获得稳定收益，才说明 DPO 对本业务值得继续投入。**

#### 3.5 阶段结论

> **核心结果：Qwen3-0.6B 从初始基模的 2/51 提升到最终 SFT 的 40/51，协议遵循率从 39.2% 提升到最终复评的 92.2%（47/51）；独立 holdout 达到 21/24。**

阶段一证明，0.6B 小模型并非天然无法完成 Agent 结构化任务。经过 LoRA SFT 和多轮错误驱动的数据迭代后，模型已经能够较稳定地完成字段提取、缺失信息追问、工具调用、工具结果处理和多轮状态更新。初始 SFT 将通过数从 2/51 提升到 24/51，后续定向迭代又将最终结果提升到 40/51；相比初始基模，最终多通过 38 条样本，有效通过率由 3.9% 提升到 78.4%。

需要说明的是，初始基模结果与最终结果之间经历了业务合同和评分器校准，因此 2/51 → 40/51 表示项目全过程的能力变化，不是单一变量的严格消融实验；各轮 SFT 和 DPO 的效果判断，仍以对应小节中的同评测口径对照为准。

最终选择 Qwen3-0.6B SFT 进入阶段二，不是因为它已经解决所有问题，而是因为其质量已经接近同路线 1.7B 候选：最终统一复评中，0.6B 与 1.7B 主集分别为 40/51 和 39/51，holdout 均为 21/24，但 0.6B 的 CPU 推理速度约为 1.7B 的 1.6 倍，部署成本更低。剩余的相对日期、非法工具名和严格协议问题不再继续依赖训练硬解，而是在后续系统中交给日期解析、Schema 校验、工具白名单和失败重试等确定性机制兜底。

### 4. 阶段二：本地推理性能优化

> **状态：** 5.1—5.8 已形成初稿。

#### 4.1 优化目标、使用场景与性能约束

阶段一已经完成模型能力优化，并最终选定 Qwen3-0.6B SFT 作为部署候选。进入阶段二后，核心问题不再是继续提高离线任务分数，而是判断该模型能否在无独立 GPU 的普通电脑上，以可接受的资源占用和响应速度稳定运行。

本阶段将优化目标分为三个层次：

1. **降低用户可感知的等待时间**：优先降低真实首 Token 延迟（TTFT），使流式界面尽快返回内容；同时缩短端到端时延，避免模型虽然能够运行，但交互体验无法使用。
2. **控制本地部署成本**：降低模型文件体积和运行内存，并保证模型可以通过 CPU 推理框架部署，不依赖消费级或数据中心 GPU。
3. **守住任务质量下限**：任何性能优化都必须重新运行冻结评测集和独立 holdout。速度提升不能只看耗时，还要同时报告格式错误、字段错误和动作判断回归；如果质量损失过大，即使推理更快也不能进入最终方案。

性能实验运行在 Windows 虚拟机中，底层 CPU 为 AMD EPYC 7763，分配 8 个物理核心、16 个逻辑处理器，使用 llama.cpp 进行单模型推理。项目基于该硬件上的实验数据分析推理耗时和性能瓶颈，并据此推断其他 CPU 设备上的性能趋势；迁移到具体设备时，再结合其核心数、主频、缓存和内存带宽重新测试实际速度。

#### 4.2 F16 推理基线、性能分析与优化方向

阶段一完成 SFT 后，项目将 LoRA Adapter 与基座模型合并，并导出未经低位宽量化的 F16 GGUF。该模型已经具备后训练获得的任务能力，只是尚未进行量化、推理参数调优和缓存优化，因此将其作为阶段二的推理性能基线。实验使用 llama.cpp、8 个推理线程并关闭 Prompt Cache，从评测集中选择 8 条不同长度的真实请求，每条重复 3 次；表中报告 24 次正式请求的中位数，另有 1 次模型与内核预热不计入结果。

| 模型 | 质量通过数 | 模型体积 | 峰值服务内存 | 输入长度 | 输出长度 | Prefill | 真实 TTFT | Decode | Decode 速度 | 端到端时延 |
|---|---:|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| F16 | 60/75 | 1142.7 MiB | 1688.8 MiB | 1447 tokens | 71 tokens | 5.76 s | 6.25 s | 2.29 s | 29.42 tokens/s | 8.78 s |

一次推理主要包含两个阶段：Prefill 处理全部输入，Decode 逐 Token 生成输出。当前任务属于“长输入、短输出”，F16 的 Prefill 约占端到端时延的 65.6%，TTFT 也主要由 Prefill 决定。因此，本项目的优化重点是减少首字前的输入计算，同时兼顾 Decode 速度和任务质量。

基于基线结果，后续从四个方向开展实验：

1. **模型量化**：降低权重精度和模型体积，减少 CPU 计算与内存读取开销；重点比较不同量化参数带来的速度收益和任务精度损失。
2. **推理参数调优**：Prefill 具有较高的并行计算空间，而 Decode 更容易受到内存带宽和线程同步影响；因此分别调整线程数、Batch 和 Ubatch，寻找当前硬件上的最佳组合。
3. **Prompt 压缩**：直接减少输入 Token 数，从源头降低 Prefill 计算量；同时使用 holdout 检查规则删减是否破坏模型的任务能力。
4. **公共前缀缓存**：跨请求复用固定系统 Prompt 对应的 KV Cache，只计算发生变化的用户输入和状态，以降低后续请求的 Prefill 和 TTFT。

#### 4.3 模型量化实验

量化实验以 F16 为原始基准，对 Q8、Q6、Q5、Q4、Q3 和两档 IQ2 进行统一比较。结果显示，Q3 和 IQ2 已出现明显能力崩塌；Q5、Q6 没有同时优于 Q4 的质量、体积和速度，因此最终保留 Q8_0 与 Q4_K_M。

| 指标 | F16 | Q8_0 | Q4_K_M |
|---|---:|---:|---:|
| 质量通过数 | 60/75 | 61/75 | 59/75 |
| 模型体积 | 1142.7 MiB | 609.8 MiB | 378.3 MiB |
| 峰值服务内存 | 1688.8 MiB | 1154.5 MiB | 1128.0 MiB |
| Prefill | 5.76 s | 6.75 s | 4.35 s |
| 真实 TTFT | 6.25 s | 7.23 s | 4.87 s |
| Decode 速度 | 29.42 tokens/s | 37.31 tokens/s | 41.89 tokens/s |
| 端到端时延 | 8.78 s | 9.80 s | 6.92 s |

其中，质量通过数来自统一的 75 条质量评测；体积、内存与延迟来自本轮本地同机连续测试。

在本轮同机连续测试中，Q4 相比 F16 将模型体积减少约 66.9%，峰值服务内存减少约 33.2%，TTFT 降低约 22.1%，端到端时延降低约 21.2%，Decode 速度提高约 42.4%；质量由 60/75 变为 59/75。Q8 保持了质量，但本轮 Prefill 和 TTFT 没有优于 F16，因此定位为质量优先的部署版本，而不是最低延迟版本。Q4 则作为允许少量质量回归的低延迟版本。

#### 4.4 推理参数调优实验

本轮实验运行在 Windows 虚拟机中，底层 CPU 为 AMD EPYC 7763，虚拟机分配 8 个物理核心、16 个逻辑处理器。线程参数与硬件拓扑直接相关：Decode 的初始线程数以 8 个物理核心为基准，Prefill 具有更大的并行空间，因此将 16 个逻辑处理器作为 `threads-batch` 的候选上限。该选择只是参数搜索的起点，最终仍由实际测量决定。

实验固定 Q4 模型、关闭 Prompt Cache，并设置 `parallel=1`。参数调优分为两步：先使用同一条约 1.3k Token 请求粗筛 12 组线程配置和 12 组 Batch/Ubatch 配置，再选取 5 组代表性参数，使用 8 条不同长度的真实请求各重复 2 次进行复核。

参数与推理阶段的对应关系如下：

- `threads` 主要控制 Decode 阶段的生成线程数；
- `threads-batch` 主要控制 Prefill 等批量计算阶段的线程数；
- `batch-size` 是逻辑批上限，`ubatch-size` 是实际执行时的物理微批上限；
- `parallel=1` 表示本轮只评估单请求延迟，不测试多请求并发。

候选配置的真实请求复核结果如下：

| 参数（threads / threads-batch / batch / ubatch） | Prefill P50 | TTFT P50 | TTFT P95 | Decode 速度 | 端到端 P50 | 端到端 P95 |
|---|---:|---:|---:|---:|---:|---:|
| 8 / 16 / 2048 / 512 | **3.76 s** | **4.26 s** | **5.97 s** | 42.96 tok/s | 6.48 s | 8.97 s |
| 10 / 16 / 2048 / 512 | 3.86 s | 4.35 s | 6.29 s | **44.10 tok/s** | **6.21 s** | 8.95 s |
| 8 / 10 / 2048 / 512 | 4.30 s | 4.78 s | 6.40 s | 42.86 tok/s | 6.85 s | 9.19 s |
| 10 / 16 / 512 / 256 | 3.88 s | 4.41 s | 6.32 s | 43.04 tok/s | 6.25 s | 8.93 s |
| 8 / 16 / 512 / 256 | 3.82 s | 4.33 s | 6.08 s | 40.35 tok/s | 6.33 s | **8.89 s** |

实验得到三个结论：

1. **Prefill 更需要并行资源**：将 `threads-batch` 从 16 降到 10 后，Prefill P50 增加约 14.4%，说明当前长输入任务可以有效利用 16 个逻辑处理器进行批量计算。
2. **Decode 线程存在性能拐点**：`threads=10` 的 Decode 速度比 `threads=8` 高约 2.7%，端到端 P50 降低约 4.1%，但 TTFT P50 反而增加约 2.2%；粗筛中继续增加到 16 线程时性能明显下降，说明更多线程带来的同步和内存竞争会抵消收益。
3. **Batch 不是越大越快**：`2048/512` 与 `512/256` 的整体差异较小，没有一个组合在 P50、P95、Prefill 和 Decode 上全面占优。Batch 参数需要与输入长度、线程配置和硬件缓存共同测试，不能仅按“能够容纳完整 Prompt”判断性能。

本项目属于长输入、短输出任务，并优先关注首字延迟，因此最终保留 `threads=8`、`threads-batch=16`、`batch-size=2048`、`ubatch-size=512`、`parallel=1`。如果应用转向长输出并更关注完整响应时间，则可以进一步考虑 `threads=10` 的配置。以上结论只适用于当前 8 物理核心、16 逻辑处理器的虚拟机；迁移到其他 CPU 时，需要使用相同方法重新寻找线程和批处理参数的拐点。

#### 4.5 Prompt 压缩实验

实验将完整 Prompt 从约 1337 tokens 压缩到约 605 tokens。冷请求 TTFT 从 5.35 秒降低到 2.84 秒，说明缩短输入能够直接减少 Prefill；但 holdout 通过数从 17/24 降到 5/24，模型丢失了大量字段边界和动作判断能力。

该结果说明，Prompt 压缩虽然有效降低延迟，但不能只以 Token 数为目标。对于 0.6B 小模型，部分看似重复的规则仍是维持任务质量所必需的，因此本项目拒绝采用激进压缩方案。后续可将 Prompt 优化作为一种低成本的持续优化手段：在保持任务准确率和输出稳定性的前提下，逐步删除冗余表达、合并重复规则，以减少输入 Token 数和 Prefill 时间。

#### 4.6 公共前缀缓存实验

本项目的系统提示词和任务规则相对固定，不同请求主要变化的是用户输入，因此可以复用公共前缀已经计算出的 KV Cache。实验使用 llama.cpp 的跨请求 Prompt Cache，在单 Slot、`parallel=1` 条件下缓存固定系统 Prompt，后续请求只需计算发生变化的部分。

| 方案 | Prefill | TTFT | 端到端时延 | Holdout 通过数 |
|---|---:|---:|---:|---:|
| 不使用公共前缀缓存 | 4.81 s | 5.35 s | 7.38 s | 17/24 |
| 命中公共前缀缓存 | 1.05 s | 1.57 s | 3.73 s | 17/24 |
| 相对变化 | 降低 78.2% | 降低 70.7% | 降低 49.5% | 无变化 |

公共前缀缓存是本阶段收益最大且没有引入新增质量回归的优化。考虑到推理服务由项目自行部署，最终采用“服务启动预热 + 运行期间复用”的方式：服务启动并加载模型后，先发送一次包含固定公共前缀的预热请求，将其 KV Cache 提前写入缓存。这样，第一个真实业务请求也可以命中公共前缀缓存；需要注意，这并未消除首次计算，而是将一次性的完整 Prefill 从用户请求阶段前移到了服务启动阶段。后续请求继续复用该缓存，从而稳定降低 Prefill、TTFT 和端到端时延。

#### 4.7 优化手段的组合与最终部署方案

四类优化作用于不同位置，最终方案不是选择其中一种，而是在质量约束下进行组合：量化降低模型体积并加快权重读取，推理参数调优使 CPU 资源与 Prefill、Decode 两个阶段更加匹配，Prompt 优化减少需要处理的输入 Token，公共前缀缓存则避免跨请求重复计算固定内容。

| 优化方向 | 最终选择 | 本项目中的主要作用 | 实验结论 |
|---|---|---|---|
| 模型量化 | Q4_K_M | 减少模型体积、内存占用和权重读取开销 | 相比 F16，体积减少 66.9%，TTFT 降低 22.1%，Decode 速度提高 42.4%，质量通过数由 60/75 变为 59/75 |
| 推理参数 | `8 / 16 / 2048 / 512`，`parallel=1` | 使 Prefill 充分利用当前 16 个逻辑处理器，同时避免 Decode 线程过多产生竞争 | 在复核候选中取得最低 Prefill P50 和 TTFT P50，更符合长输入、短输出场景 |
| Prompt 优化 | 保留完整规则，后续进行保守精简 | 直接减少输入 Token 和 Prefill 计算量 | 激进压缩虽将 TTFT 降低 46.9%，但质量明显下降，因此不进入最终方案；下一轮以精简约 10%—15% 且 holdout 结果不下降为目标 |
| 公共前缀缓存 | 启动预热 + 运行期间复用 | 跳过固定系统 Prompt 的重复 Prefill | 缓存命中时 Prefill 降低 78.2%，TTFT 降低 70.7%，端到端时延降低 49.5%，holdout 结果不变 |

最终部署采用 Q4_K_M 模型和 `threads=8`、`threads-batch=16`、`batch-size=2048`、`ubatch-size=512`、`parallel=1`，保留当前通过质量验证的完整 Prompt，并在服务启动阶段预热公共前缀缓存。Prompt 精简暂不计入最终性能收益，只有在重新通过完整 holdout 后才合入部署版本。

#### 4.8 阶段结论

> **核心结果：模型从 1142.7 MiB 压缩到 378.3 MiB，TTFT 从 6.25 秒降至 1.57 秒，端到端时延从 8.78 秒降至 3.73 秒，Decode 从 29.42 提升到 41.89 tokens/s；质量通过数仅由 60/75 变为 59/75。**

换算后，最终方案实现了 **模型体积减少 66.9%、首字等待减少 4.68 秒、端到端等待减少 5.05 秒、Decode 速度提高 42.4%**。也就是说，模型缩小到原来的约三分之一，首字响应接近原来的四倍快，完整响应速度达到原来的约 2.35 倍，而质量评测只减少 1 条通过样本。

这些收益来自四个方向的组合：Q4_K_M 量化降低模型体积、内存占用和权重读取开销；推理参数调优使 CPU 资源与 Prefill、Decode 两个阶段更加匹配；Prompt 实验明确了输入长度对 Prefill 的直接影响，并确定后续只进行不破坏任务规则的保守精简；公共前缀缓存则利用系统提示词稳定的特点，消除跨请求的重复 Prefill。

以下对比中的 F16 基线并非未经后训练的原始基座模型，而是阶段一完成 SFT、合并 LoRA 权重后导出的 F16 GGUF；它尚未进行阶段二的量化、推理参数调优和缓存优化。最终 Q4_K_M 缓存命中方案的代表性指标对比如下。由于 F16 基线与缓存实验来自两组测试，输入长度和运行批次并非完全一致，因此该表用于说明最终方案的整体性能量级，四项优化的严格增量仍以前述各小节的同条件对照实验为准。

| 指标 | SFT 后 F16 推理基线 | 最终部署方案 | 整体变化 |
|---|---:|---:|---:|
| 模型体积 | 1142.7 MiB | 378.3 MiB | 减少 66.9% |
| 峰值服务内存 | 1688.8 MiB | 1128.0 MiB | 减少 33.2% |
| Prefill | 5.76 s | 1.05 s | 降低约 81.8% |
| TTFT | 6.25 s | 1.57 s | 降低约 74.9% |

在当前 AMD EPYC 7763 虚拟机、8 个物理核心和 16 个逻辑处理器的实验环境中，上述结果证明：经过量化、参数调优和缓存优化后，0.6B 本地模型能够在仅增加轻微质量损失的情况下，显著降低普通 CPU 场景中的模型体积和用户等待时间。其中，公共前缀缓存贡献了最大的首字延迟收益，Q4_K_M 量化同时改善了部署资源与 Decode 速度，参数调优提供了适配当前硬件的稳定配置；Prompt 则保留质量优先原则，后续只进行小步精简和逐轮回归。

## 第二部分：理论基础与应掌握知识

### 1. 大模型后训练理论

#### 1.1 DPO 的理论基础：解决什么问题，适合什么任务？

> **对应实践：** 第一部分 4.4。本节根据 DPO 原论文和训练框架文档介绍通用原理，不将本项目未获得收益的结果推广为算法本身无效。

**1. DPO 要解决什么问题？**

DPO（Direct Preference Optimization，直接偏好优化）利用“同一个问题，哪个回答更好”的比较数据，让模型更倾向于生成符合目标要求的回答。[1]

可以先用一句话区分：**SFT 通过正确示例教模型怎么回答；DPO 通过优劣对照，进一步调整模型更倾向于给出哪种回答。** 两者并不互斥，常见路线是先通过 SFT 建立任务能力，再通过 DPO 优化回答质量或行为偏好。

例如，用户要求“用一句话解释缓存”。两个回答都正确，但一个简洁且直接，另一个长篇展开。若目标是遵循用户的简洁要求，就可以把前者标为更优回答。但偏好不限于语气或风格，也可以依据事实正确性、指令遵循程度、安全性或任务完成质量来确定。

**2. 训练数据是什么样，模型如何学习？**

一条典型 DPO 数据包含三部分：[2]

- `prompt`：相同的问题和上下文；
- `chosen`：根据明确标准选出的更优回答；
- `rejected`：相对较差的回答，不一定完全错误。

这与 Contrast Sets 不同：Contrast Sets 通常改变输入中的关键条件，并相应改变正确答案；DPO 则固定输入，比较两个候选输出。

标准 DPO 使用一个待训练模型和一个固定的参考模型，参考模型通常取 DPO 开始前的 SFT 模型。训练目标是：**相对于参考模型，提高 chosen 对 rejected 的相对生成概率。** 它不是训练一个在推理时挑选答案的分类器，而是直接更新生成模型；也不保证每条 chosen 的绝对概率都会上升，关键是两者的相对偏好发生变化。[1][2]

理论上，DPO 从“提高偏好奖励，同时限制模型偏离参考模型”的目标出发，利用奖励与策略概率之间的关系，将偏好学习转化为一个成对分类损失。相比先训练奖励模型、再用 PPO 优化生成模型的经典 RLHF 流程，标准离线 DPO 不需要单独训练显式奖励模型，也不需要在优化过程中反复在线采样回答。[1] 偏好对仍需提前收集或生成，并经过可靠标注。

**3. β 参数起什么作用？**

β 控制偏好优化与保持参考模型行为之间的权衡。在 DPO 对应的 KL 正则化目标中，较大的 β 表示更强的偏离惩罚；它不是学习率，也不能简单理解为“越大，模型就越激进地学习偏好”。[1][2]

实际效果还受学习率、训练轮数、偏好数据和模型状态影响。因此，比较 `β=0.1` 与 `β=0.3` 时，应报告任务质量和回归情况，不能仅凭 β 变大就断言发生了更严重的分布偏移或遗忘。

**4. DPO 适合什么任务？**

原论文在情感控制、摘要和单轮对话上进行了实验。[1] 从方法原理出发，以下情况值得考虑 DPO；后两类属于应用方向，不是原论文对本项目的效果保证。

| 任务类型 | 可以用什么标准构造偏好 |
|---|---|
| **对话与指令遵循** | 回答是否切题、清楚，是否遵守长度和格式要求 |
| **摘要与内容生成** | 是否保留重点、忠实于原文，减少冗余或无依据内容 |
| **风格、安全与交互行为** | 是否符合目标语气，是否恰当拒答、澄清，而不是盲目服从或过度拒绝 |
| **可验证的代码、推理或工具调用** | 根据测试、规则或任务结果，区分更可靠的答案与存在错误的答案 |

**适用的关键不是“必须有多个正确答案”，而是能否为同一输入构造可靠、有学习价值的优劣对。** 即使任务只有一个正确答案，也可以将正确与错误输出构造成偏好对；TRL 文档也支持工具调用形式的 DPO 数据。[2] 但能组织成偏好对，不等于一定比 SFT 更有效。

**5. 什么情况下不应优先使用 DPO？**

- **基础任务还不会做。** 如果模型连字段含义、业务规则和基本格式都没有学稳，通常先完善 SFT 更直接。DPO 不是补齐任意知识或推理能力的保证。
- **偏好标签不可靠。** 如果 chosen 本身有错误，或标注者对“更好”的标准不一致，训练可能强化错误方向；若优劣只与长度等表面特征相关，还可能学偏。
- **需要精确修复局部错误。** 标准 DPO 使用整段答案的成对信号，不会自动提供“具体哪个字段为何错误”的监督。它仍可能改善此类问题，但需通过针对性偏好数据和评测确认，不能保证逐字段修复。
- **优化指标与业务目标不同。** 偏好对排序更准确、DPO loss 更低，不代表实际生成的 JSON、日期或工具参数更准确，仍需检查任务通过率和旧能力回归。

对应 4.4，更严谨的解释是：**本项目测试的 DPO 配置没有获得稳定收益，因此当前选择保留 SFT；基础能力不足、偏好数据与任务指标不匹配等是待验证的可能原因，而不是已经证明的因果结论。** 不能仅凭“任务有唯一答案”认定 DPO 不适用，也不能将一次无收益实验推广为 DPO 无法改善事实、推理或结构化任务。

2. Hugging Face TRL，*DPO Trainer*：<https://huggingface.co/docs/trl/dpo_trainer>。说明 prompt/chosen/rejected 数据结构、标准 DPO 损失、参考模型、β 参数及工具调用数据支持。

### 2. 数据集理论

#### 2.1 如何制作 SFT 数据集？

> **对应实践：** 第一部分 4.3.1。本节介绍从任务规则到训练样本的构造方法，以及 Contrast Sets 在其中的作用。

**1. SFT 数据是在教模型什么？**

SFT 使用“输入 → 正确输出”的示例，让模型学习在给定上下文中生成目标答案。对于对话任务，输入可以包含系统指令、历史消息、用户请求和工具结果；正确输出则是模型下一步应该生成的回复或工具调用。训练时，模型通过提高目标答案中各个 Token 的预测概率，学习输入与输出之间的关系。

因此，数据制作不能只有“题目看起来合理”，还必须保证答案符合题目条件。例如，用户没有提供时间，标准答案就不能自行编造时间或直接调用需要时间参数的工具。对于本项目这类严格结构化任务，格式正确和业务判断正确同样重要。

**2. 一套实用的数据制作流程是什么？**

可以按照以下流程组织，具体检查规则由任务决定：

1. **先定义任务和正确答案。** 明确需要哪些字段、何时追问、何时调用工具，以及输出格式和多轮状态更新规则。
2. **编写覆盖主要场景的基础样本。** 既有信息完整的正常流程，也有缺失信息、用户修改要求、工具失败和确认拒绝等情况，不能只有一种动作。
3. **扩充不同表达和困难场景。** 可以人工编写，也可以用较强模型生成候选样本。Self-Instruct 就提出从少量人工任务出发，生成新指令、输入和答案，再经过筛选形成指令训练数据的流程。[1] 它说明了自动构造数据的可行性，但不意味着模型生成的答案天然正确。
4. **检查答案、格式和重复。** 校验 JSON、字段、工具名和参数，再检查业务逻辑；修正错误或冲突标签，并对合成数据进行人工抽检。对于允许多种合理答案的任务，不能把措辞不同直接当成标签冲突。
5. **隔离训练与评测数据。** 在扩充之前按来源或场景实例划分数据，同一原始样本及其改写、变体放在同一侧，并检查跨集合近重复。研究表明，训练与评测语料重复可能抬高评估结果。[3] 仅仅“不是逐字相同”不代表没有泄漏。

**3. Contrast Sets 如何帮助构造数据？**

Contrast Sets 的核心思想是：**保持大部分内容不变，只改变一个影响答案的关键条件，检查正确答案是否随之变化。** Gardner 等最初将它用于测试模型是否理解局部决策边界，而不是提出一种 SFT 算法。[2] 如果把这个思路借用到训练数据制作中，就可以构造下面这样的对照样本：

| 输入 | 正确行为 | 与完整信息样本相比改变了什么 |
|---|---|---|
| 预约明天下午三点，做 60 分钟 | 调用工具 | 信息完整 |
| 想预约，做 60 分钟 | 追问时间 | 去掉时间 |
| 预约明天下午三点 | 追问时长 | 去掉时长 |

普通改写是在教模型“不同说法可能表达同一个意思”；这种对照构造则是在教模型“条件不同，行为也必须不同”。构造时要检查完整上下文：如果历史消息已经给出了时间，只删除当前一句中的时间，并不一定意味着应该追问。

用于 SFT 时，每条对照样本仍然是普通的“输入 → 正确输出”，与基础训练样本混合即可，不需要增加对比学习损失，也不是 DPO 的 chosen/rejected 偏好对。数据去重时，也不应把这些有意义、标签正确的边界变体仅因文字相似而全部删除。

**本节结论：SFT 数据制作的重点不是机械地增加问答，而是让主要场景有覆盖、每条答案有依据、容易混淆的条件有对照，并保证评测数据独立。** 第一部分只有在实际训练样本确实采用了这种关键条件对照构造时，才适合称为“借鉴 Contrast Sets 的数据增强”；论文提供方法依据，并不能代替对本项目数据的核查。

**参考资料：**

1. Wang et al.，*Self-Instruct: Aligning Language Models with Self-Generated Instructions*，ACL 2023：<https://aclanthology.org/2023.acl-long.754/>。支持从人工种子任务出发，自动生成并筛选指令数据的流程。
2. Gardner et al.，*Evaluating Models’ Local Decision Boundaries via Contrast Sets*，Findings of EMNLP 2020：<https://aclanthology.org/2020.findings-emnlp.117/>。支持关键条件变化与答案变化的对照构造思想；原论文用途是评估，本文将其借鉴到数据增强。
3. Lee et al.，*Deduplicating Training Data Makes Language Models Better*，ACL 2022：<https://aclanthology.org/2022.acl-long.577/>。支持训练数据去重和跨集合重复检查的原则；不是本项目中文 SFT 去重阈值的直接依据。

#### 2.2 SFT 数据集做多少合适，什么时候可以停止？

> **对应实践：** 第一部分 4.3.3。本节解释如何判断数据量是否够用，而不是给出一个适用于所有模型的固定条数。

**1. 为什么没有统一的数据量标准？**

SFT 所需数据量取决于基座已经会什么、任务有多复杂，以及样本是否准确且具有代表性。如果模型已经理解任务，只需学习固定输出格式，所需示例可能较少；如果还要学习复杂的多轮状态变化、业务规则和条件组合，就需要更充分的覆盖。大量重复或错误样本，不能替代缺失的关键场景。

LIMA 研究使用 1000 条精心整理的问答，对 65B LLaMA 进行 SFT，展示了少量高质量数据也能取得较好的指令遵循效果。[1] 但它不能证明“所有任务用 1000 条就够”：该研究使用的模型规模、已有能力和任务，与本项目的 0.6B 结构化任务不同。论文的启示是重视数据质量，而不是照搬样本数。

**2. 哪些条件会影响所需数据的量级？**

判断数据规模，首先要看“模型还需要学习多少种不同情况”，而不是只看模型参数量。下面是结合文献与任务特点整理的选型原则，不是固定的数据量公式。[1][3][4]

| 影响条件 | 可以从较少数据开始的情况 | 往往需要扩大数据规模的情况 |
|---|---|---|
| **任务范围** | 单一业务、少数明确任务 | 同时覆盖问答、写作、翻译、代码等多种任务 |
| **基座已有能力** | 已经理解相关语言和任务，主要学习格式或业务规则 | 对目标领域、语言或所需推理能力掌握不足；此时增加数据也不一定能弥补全部缺口 |
| **输入多样性** | 输入来源、语言和表达类型相对集中 | 跨领域、多语言、多种文档格式，以及大量口语、噪声和歧义 |
| **决策与状态复杂度** | 字段和动作有限，条件组合简单 | 工具种类多、交互链路长，多轮状态和条件组合复杂 |
| **目标质量与边界覆盖** | 验证主要流程，允许明确的能力边界 | 要求更低的关键错误率，需要补充罕见场景和困难反例 |
| **样本质量与信息量** | 标签准确、覆盖互补，每条样本提供有效变化 | 重复多、配比失衡或标签冲突；应先清理和补缺，不能靠堆数量解决 |

从这些条件出发，可以理解三种典型情形：

- **已有能力的格式或风格适配**：可以先用几十到几百条高质量示例做试验。OpenAI 的 SFT 指南建议从约 50 条示例开始评估，但这是其支持模型上的起步建议，不是所有本地模型的最低需求。[5]
- **边界明确的领域任务**：可以从几百到几千条代表性样本做初始实验，再按错误类型扩充。这是实验起点的建议，不是文献给出的充分性保证；任务一旦包含大量复杂组合，所需规模可能明显上升。
- **广泛的通用指令或复杂多任务训练**：往往需要更大的数据池来覆盖不同任务和表达。例如 Alpaca 使用约 5.2 万条指令样本；FLAN 的研究覆盖约 1800 种任务，后者是任务数而非样本数。[4][6] 这些案例说明训练目标不同会带来规模差异，不代表数万条就是统一门槛。

此外，“条数”不是完整的规模指标：一条短问答与一条长多轮对话提供的训练信号不同，比较数据集时还应说明任务分布、对话轮数和有效训练 Token 数。把同一条样本重复训练更多轮，也不等于增加了新的场景覆盖。

**对本项目的意义：** 固定业务字段、有限动作与工具集合，以及复用基座已有语言能力，能够解释为什么可以从约千条领域数据开始，而不是直接采用通用指令训练的规模。但多轮状态和严格动作判断仍然可能很难，“输出 JSON”或“模型参数少”都不能单独作为少量数据足够的理由。**任务特点决定从什么规模开始，验证收益决定是否需要继续扩大。**

**3. 如何判断继续增加数据有没有价值？**

可以使用“学习曲线”的思路：比较不同训练数据量下的验证表现，看增加数据是否仍能带来提升。[2] 不一定需要画图，记录实验表即可。例如：

- 在训练池中按任务类型抽取 25%、50%、100% 的数据，各档尽量保持相近的场景配比，并让小档数据包含在大档中；
- 从同一个基座出发，使用一致的 LoRA 设置和训练策略，分别训练，而不是在上一档模型上直接续训；
- 使用同一套验证集，比较任务通过率、主要场景表现和旧能力退步情况。

OpenAI 的微调实践文档也建议比较“半量数据”和“全量数据”的训练效果，以估计继续增加数据的价值。[3] 对本项目而言，这是可借鉴的实验方法，不是已经完成的数据量消融实验。记录时还应注明训练轮数、总 Token 和更新步数：同样训练轮数下，数据更多也意味着计算量更多，因此结果不能全部归因于样本数量。

判断时可以简单分为三种情况：

- **增加数据后，验证表现仍明显提高**：说明新增数据仍有价值，可以继续补充。
- **表现趋于稳定，而且达到阶段目标**：可以停止同类数据扩充，保留验证表现最好的模型。
- **表现趋于稳定，但仍未达到目标**：不能说“数据已经够用”，应检查标签、场景覆盖、训练配置和模型能力，而不是继续机械地增加同类样本。

评测集较小或结果波动时，应重复关键实验或扩大验证集，不能根据一两道题的变化判断效果已经到顶。

**4. “数据够了”和“训练该停了”有什么区别？**

“数据够了”关注的是：**再加入新的有效样本，还有没有收益？** “训练该停了”关注的是：**同一批数据继续训练更多轮，还有没有收益？** 两者不能只靠训练 loss 判断。

实践中应根据验证集选择训练轮数和 checkpoint：如果训练 loss 继续下降，但验证任务表现不再改善甚至变差，就不应仅为了更低的 loss 继续训练。验证集用于反复调整数据和训练配置；最终测试集应留到方案确定后再使用，不能每轮查看测试错误并据此补训练数据，否则它就不再是独立的最终检验。[2]

**本项目可采用的停止判断是：主要任务达到阶段要求，继续补同类数据或增加训练轮数不再带来稳定收益，最后再用独立测试确认效果。** 当前约 1200 条数据是项目迭代得到的规模，不是理论推导出的最优值；4.3.3 的结果支持阶段性停止当前路线，但不等于已经通过严格实验证明数据充分。

2. scikit-learn，*Validation curves: plotting scores to evaluate models*（含 Learning curve 小节）：<https://scikit-learn.org/stable/modules/learning_curve.html>。提供比较数据量与验证表现的一般监督学习方法，不是针对大模型的样本数定律。

### 3. 模型量化

#### 3.1 GGUF、Q8、Q4_K_M 与 K-Quant

模型推理需要反复从内存读取权重并执行矩阵运算。权重量化将 F16/BF16 权重映射到更低位宽的离散数值，从而减少模型文件、运行内存和权重读取量。对于容易受到内存带宽限制的 CPU 推理，模型变小后可能获得更高的缓存命中率和吞吐；但量化内核还需要进行解包、缩放或反量化，因此低位宽并不保证所有推理阶段都更快，实际性能取决于量化格式、CPU 指令集和推理框架的内核实现。

量化会引入近似误差。位宽越低，可表示的数值等级越少，权重与原始值之间的偏差通常越大。这些偏差经过多层 Transformer 累积后，可能改变最终 Token 的概率排序。对于严格 JSON、字段枚举和工具调用任务，即使只改变一个标点、字段或动作，也会使整条样本判错，因此不能只用模型体积或通用困惑度判断量化版本是否可用，还必须运行任务级评测。

Q8、Q6、Q5、Q4 等名称表示不同的权重量化档位，但 llama.cpp 的 K-Quant 并不是简单地将全部参数统一压缩到同一位宽。K-Quant 将权重按 block 和 super-block 分组，并为每组保存缩放参数；`Q4_K_M` 中的大部分权重采用 Q4_K，部分更敏感的 Attention 和 FFN 张量会使用 Q6_K，输出张量也保留较高精度。因此，`Q4_K_M` 更准确的理解是“以四位为主体的混合精度量化”，其目标是在体积、速度和质量之间取得平衡。

不同量化档位的任务分数不一定严格单调。更高位宽通常意味着更低的平均量化误差，但有限评测集使用的是离散通过数，一两个边界样本的变化就可能改变排序；不同格式还会对不同张量产生不同误差，并调用不同的 CPU 内核。因此，某次实验中 Q4 的通过数高于 Q5，并不证明四位量化天然比五位量化准确，只能说明 Q5 在当前模型、量化工具、硬件和任务集上没有表现出综合优势。

#### 3.2 imatrix 与校准数据

不同权重对模型输出的重要性并不相同。AWQ 等研究表明，少量显著权重或通道会对模型质量产生较大影响；如果对所有权重使用完全相同的量化策略，重要信息可能被低位宽误差破坏。

llama.cpp 的 Importance Matrix（imatrix）使用校准文本运行原始模型，收集中间激活统计，并估计不同权重对实际计算结果的影响。量化器据此优先保护更重要的权重，降低关键部分的量化误差。其流程可以概括为：

```text
代表性校准数据
      ↓
运行原始模型并收集激活统计
      ↓
生成 Importance Matrix
      ↓
指导低位宽量化中的误差分配
```

校准数据应覆盖真实任务中的语言、格式和输入分布，同时与评测集隔离。imatrix 可以改善量化质量，但不能保证量化无损：如果位宽过低、校准数据覆盖不足，或模型本身参数较少，剩余误差仍可能破坏任务能力。

#### 3.3 如何分析量化实验结果

量化实验应同时比较四类指标：任务质量、模型体积与内存、Prefill、Decode。它们反映的是不同问题：

- **质量变化**反映量化误差是否破坏了模型的决策边界；
- **模型体积与内存**反映压缩收益，以及权重读取压力是否降低；
- **Prefill**偏向大批量矩阵计算，其收益取决于低位宽计算内核的效率；
- **Decode**需要逐 Token 反复读取权重，通常更容易从模型缩小和内存带宽下降中受益。

在本项目的实验中，Q8 的任务通过数与 F16 接近，Decode 更快，但 Prefill 反而更慢。结合量化推理原理，一种合理解释是：Q8 减少权重读取量带来的收益，在本轮 CPU、llama.cpp 版本和 Prefill 工作负载下，未能覆盖解包、缩放以及对应量化内核的额外开销。该解释只用于说明本次实验现象，不代表 Q8 在其他模型、硬件或推理框架上一定比 F16 的 Prefill 更慢。

同样，在本项目的同机测试中，Q4_K_M 同时降低了模型体积、Prefill 和 Decode 耗时。这说明当前 Q4_K_M 格式与 llama.cpp 的 Q4_K CPU 内核，在本轮硬件和请求长度下取得了更有利的权重读取、缓存利用与计算开销平衡；不能据此推导 Q4 在所有设备上都一定比 Q8 或 F16 更快。

本项目继续降低到 Q3 和 IQ2 后，实际出现了重复字段、错误参数和 JSON 截断。结合低位宽会增加权重近似误差这一理论，可以判断这些格式在当前 0.6B 模型和结构化输出任务上已经超过可接受的误差范围。该结论的适用边界是本项目的模型、量化方法、校准数据和评测集，而不是对所有 Q3、IQ2 模型的通用判断。

小参数模型通常需要更谨慎地评估极低位宽。0.6B 模型本身的参数冗余和能力余量有限，后训练形成的结构化决策边界可能较脆弱；从四位继续压缩到三位、二位时，少量 Logit 排序变化就可能导致动作或字段错误。此时即使模型更小，也不具备实际部署价值。

量化选型最终不是寻找“位宽最低”的模型，而是在以下约束中寻找 Pareto 边界：

```text
任务质量损失可接受
        +
模型体积与内存满足部署条件
        +
Prefill、Decode 和 TTFT 确实获得收益
```

### 4. 推理与性能基础

#### 4.1 KV Cache 与跨请求 Prompt Cache

大模型采用自回归方式生成文本：每生成一个新 Token，都需要关注此前已经出现的 Token。缓存机制的核心作用是保存已经完成的注意力计算结果，避免对相同上下文重复计算。在 llama.cpp 中，需要区分请求内 KV Cache 和跨请求公共前缀缓存，两者保存的都是注意力层的 Key/Value 状态，但复用范围不同。

**请求内 KV Cache。** 在同一次请求的 Decode 阶段，模型生成第一个 Token 后，会继续逐 Token 生成后续内容。KV Cache 保存此前输入和已生成 Token 的 Key/Value，使下一个 Token 只需计算新增位置，而不必重新计算整段历史上下文。这是现代大模型推理的基础机制，llama.cpp 通常默认使用。其主要价值是避免 Decode 计算量随上下文反复累积；上下文长度、并发 Slot 数以及 KV Cache 的数据类型会共同影响内存占用。在本项目中，由于输出较短，Decode 不是最大的时延来源，因此请求内 KV Cache 是必要的推理基础，但不是本轮最主要的优化变量。

**跨请求公共前缀缓存。** 常规 KV Cache 的生命周期通常局限于一次请求或一次会话；如果多个独立请求拥有完全相同的系统提示词、工具定义或任务规则，推理服务还可以保留这段公共前缀对应的 KV 状态，并在后续请求中复用。缓存命中后，只需从第一个不同 Token 开始继续 Prefill，因此它主要减少的是重复前缀的 Prefill 和 TTFT，而不是提高单个 Token 的 Decode 速度。这类能力在不同推理框架中通常称为 Prompt Cache、Prefix Cache 或 Automatic Prefix Caching。

公共前缀缓存要求 Token 序列一致，而不仅是文本语义相同。系统 Prompt、聊天模板、工具定义或前缀中的任意 Token 变化，都可能缩短可复用的公共前缀；缓存也会受到上下文容量、并发调度、Slot 替换和服务重启影响。因此，工程上通常将稳定内容放在 Prompt 前部，将动态用户内容放在后部，并通过缓存命中日志验证实际复用长度。

对于固定前缀服务，常见部署方式是启动预热：模型加载完成后，由服务端主动发送一次包含固定前缀的请求，提前建立对应的 KV Cache。第一个真实业务请求因而可以直接复用该前缀，但预热本身仍需要执行一次完整 Prefill。该方案优化的是用户可感知的首个请求延迟，并未降低服务冷启动所需的总计算量；服务重启、缓存失效或请求被调度到未预热 Slot 后，仍需重新计算和建立缓存。

#### 4.2 Context、Batch、Ubatch、Threads 与并发

推理参数并不存在适用于所有设备和任务的固定最优值。参数选择首先受模型大小、量化格式、CPU 与内存带宽、GPU 显存、上下文长度和并发数约束；在满足容量要求后，还需要根据实际任务的 Prefill、Decode、TTFT 和吞吐表现寻找性能拐点。因此，硬件信息更适合用来确定安全的初始配置和候选范围，而实测结果才是选择最终参数的依据。

**GPU 层卸载。** llama.cpp 使用 `-ngl` 或 `--n-gpu-layers` 控制交给 GPU 执行的模型层数。这里的“卸载”是将模型层的权重和相应计算从 CPU/RAM 路径转移到 GPU/显存路径。存在可用 GPU 时，可请求尽可能多地卸载模型层，但实际数量仍受显存容量限制，应以启动日志报告的卸载层数和显存占用为准；纯 CPU 环境无需卸载，可设置 `-ngl 0`，需要明确排除 GPU 设备时可使用 `--device none`。GPU 层数的选择首先是容量问题：除了模型权重，还必须为 KV Cache、计算缓冲区和上下文增长保留空间。

**Decode 线程。** `-t` 或 `--threads` 主要控制逐 Token 生成阶段使用的 CPU 线程数。llama.cpp 官方性能建议明确指出，线程不是越多越快；线程过多可能造成调度、同步、缓存和内存带宽竞争，使 Token 生成速度下降。物理机可先以物理核心数作为正常配置参考，但不应直接认为全部逻辑处理器一定最快。如果生成异常缓慢，官方建议先测试 `-t 1`：若单线程反而更快，说明原配置可能发生了线程过饱和。不确定最佳值时，可从 1 开始逐步翻倍测试，在性能不再增长或开始下降后回退到较优值。由此可见，“物理核心数”是启发式起点，`-t 1` 是异常排查和搜索的最低候选，最终选择应以稳定的 Decode tokens/s 为准。

虚拟机通常只能可靠获知分配给来宾系统的 vCPU 数，而不能断言这些 vCPU 对应多少个独占物理核心。此时不应把 vCPU 直接当作物理核心，而应在不超过可用 vCPU 的范围内测试少量候选值。例如 8 vCPU 环境可比较 `-t 1`、`-t 2`、`-t 4` 和 `-t 8`。实验结论应限定为“当前 VM 资源配置和宿主机负载下的较优值”，不能直接推广到所有 8 核或 8 vCPU 设备。

**Prefill 线程与批处理。** `--threads-batch` 主要控制 Prompt Prefill 等批量计算阶段的 CPU 线程数，其最佳值可能与 Decode 的 `--threads` 不同。`--batch-size` 表示单次逻辑批次可容纳的最大 Token 数，`--ubatch-size` 表示计算时实际执行的物理微批上限。较大的 Batch/Ubatch 可能提高 Prefill 并行度，但也会增加峰值内存和工作缓冲区，并不保证持续加速；达到硬件并行度或内存带宽上限后，继续增大可能无收益甚至变慢。因此，这些参数需要结合典型输入长度、内存上限和 Prefill 指标测试，不能只按照“越大越好”的原则设置。

**Context 与并发。** `--ctx-size` 决定可使用的上下文容量，并影响 KV Cache 占用；上下文越大，通常需要预留的内存越多。并发数会进一步放大 KV Cache 和运行时缓冲区需求。单请求交互场景通常优先优化 TTFT 和 Decode 延迟；长文档或 RAG 场景更重视 Prefill；多用户服务则需要在吞吐、P95 延迟和内存占用之间权衡。因此，在比较线程和批处理参数时，应固定模型、量化、上下文、并发、Prompt 和输出长度，避免把工作负载变化误判为参数收益。

工程上可采用“硬件检测、少量候选实测、缓存结果”的流程：先依据可用 CPU/vCPU、RAM、GPU 和显存生成安全候选，再使用 `llama-bench` 或代表性真实请求分别测量 Prefill 与 Decode；每组重复多次，选择速度较高且波动较小的配置，并将结果与模型、量化、运行时版本和硬件环境绑定保存。模型、驱动、llama.cpp 版本、上下文、并发或 VM 资源发生变化时，应重新验证。需要注意，自动检测只能提供合理默认值，短基准测试用于寻找当前设备和任务下接近最优的参数，而不是保证找到适用于所有负载的全局最优值。

本节中有关 `--threads` 和 `--n-gpu-layers` 的选择原则来自 llama.cpp 的 Token 生成性能建议。该资料是一篇针对 Token 生成异常缓慢的专项排查文档，重点是 GPU 是否实际参与计算以及 CPU 是否线程过饱和，并不是完整的参数调优手册；它没有给出 `--threads-batch`、`--batch-size`、`--ubatch-size`、NUMA、KV Cache 和并发数的完整选参规则。上述其他参数虽然同样重要，但分别影响 Prefill、内存容量或服务吞吐，需要结合官方参数说明和基准测试工具单独评估。

### 5. 拓展提醒：vLLM 是什么，为什么值得了解？

> **为什么在这里补充 vLLM？** 如果你想面试大模型推理、模型部署或推理性能优化相关岗位，vLLM 是经常会接触到的推理服务框架，值得提前了解。这里把它写进来，主要是给大家提个醒：除了本项目的本地部署实践，还应该补充服务端、多请求并发场景下的推理知识。这一节只是入门提示，不是完整教程。
>
> **本项目实际使用的是 llama.cpp，并未使用 vLLM 完成部署或性能测试。** 下面介绍的是拓展知识，不能直接写成自己的 vLLM 项目经验。

#### 5.1 vLLM 是什么？

vLLM 是开源的大模型推理与服务框架，负责加载模型、管理推理资源、调度请求并生成输出，常用于 GPU 上的大模型在线服务。它不是一个模型，也不是 SFT / DPO 训练算法；可以理解为让模型以服务形式高效运行的一套基础设施。除推理引擎外，它还提供 OpenAI 兼容的服务接口，方便应用接入。接口兼容不代表请求被发送给 OpenAI：模型可以部署在自己的服务器上运行。

它关注的不只是“一个请求生成得有多快”，还有“多个请求同时到达时，如何在有限显存中尽量提高吞吐，并控制请求延迟”。理解它可以先抓住两点：**如何管理 KV Cache，以及如何调度不同请求的计算。**

#### 5.2 基本原理一：PagedAttention 与分块 KV Cache

前面已经介绍过 KV Cache：模型生成新 Token 时，可以复用历史 Token 的 Key/Value，避免重复计算历史位置的 K/V。不过，缓存需要占用显存，而且不同请求的输入长度、生成长度和结束时间各不相同。如果给每个请求预留一大块连续空间，容易产生预留浪费与内存碎片，限制可同时服务的请求数。

vLLM 的代表性设计是 **PagedAttention**。它借鉴操作系统分页管理的思路，将每条序列的 KV Cache 按固定数量的 Token 分成逻辑块，再通过块表映射到实际的物理存储块：

- **不要求连续存储：**一条请求的逻辑块可以映射到不连续的物理块，注意力计算通过映射读取对应的 K/V。
- **按需分配与回收：**随着序列增长申请新的块，请求结束后回收不再需要的块，减少大块预留造成的浪费。
- **支持块共享：**在满足复用条件时，不同序列可以共享已有缓存块；需要修改共享块的场景，可以通过引用计数与写时复制等机制管理。

直观理解：不是提前给每个请求占满一条最长的“连续车位”，而是按实际需要分配小块，再记录它们的位置。**它优化的是 KV Cache 的存储与访问组织，不是降低模型精度的量化算法，也不意味着注意力计算被省略。** 分页仍有块表等管理开销，最后一个块也可能存在未使用空间，不能理解为完全没有浪费。

#### 5.3 基本原理二：Continuous Batching（连续批处理）

自回归生成通常逐步推进，不同请求却不一定在同一时刻完成。如果采用固定批次，必须等一批请求全部完成后再启动下一批，短请求结束后就可能留下未被及时利用的计算容量。

连续批处理允许服务端在生成迭代之间更新活跃请求集合：完成的请求退出，在资源和调度策略允许时加入等待中的请求。例如 A、B 正在生成，A 结束后，可以让 C 加入后续计算，而不必一直等待 B 完成。这样可以更灵活地组合工作负载，提高多请求场景下的资源利用率。

**PagedAttention 解决缓存如何分配和访问，连续批处理解决请求如何进入和退出计算批次。** 两者相互配合，但不是同一个技术。吞吐提高也不代表每个请求都更快：并发过高会增加排队时间，仍需在吞吐、显存容量、首 Token 延迟（TTFT）和每输出 Token 时间（TPOT）之间权衡。

#### 5.4 与本项目的联系，以及面试前可以补什么

vLLM 也支持前缀缓存复用。多个请求拥有一致且可复用的 Token 前缀时，可以复用对应 KV 状态，减少重复 Prefill；这与本项目公共前缀缓存的思路相通，但不能把 llama.cpp 的实测数字直接套到 vLLM 上。**PagedAttention 是分块管理机制，前缀缓存是复用策略，两者也不能混为一谈。**

本项目偏向小模型、GGUF 量化与本地 CPU 推理；vLLM 则值得从服务端高并发与加速器资源管理的角度学习。这是本项目的选型侧重点，不是说 llama.cpp 不能使用 GPU，或 vLLM 只能使用 GPU。

如果准备推理相关岗位，建议至少能回答以下问题：

1. **Prefill 和 Decode 有什么区别？** 为什么长输入与长输出对应的性能瓶颈可能不同？
2. **KV Cache 为什么会限制并发？** 上下文长度、并发序列数、KV 头数和缓存精度如何影响占用？
3. **PagedAttention 与连续批处理各解决什么问题？** 为什么提高吞吐不一定降低单请求延迟？
4. **如何做服务压测？** 固定模型、硬件、输入输出长度与负载条件，观察吞吐、TTFT、TPOT、P95 延迟和显存占用，区分冷启动、预热与缓存命中。

有条件时，可以用兼容环境和可容纳的模型跑通一次 vLLM 服务，做几组并发压测，再进一步学习分块 Prefill、前缀缓存与多卡并行。**这里的目标是提醒大家补齐知识面，不是要求每位同学都把 vLLM 加进本项目或简历。**

## 第三部分：面试问题

**项目包装与迁移思路：找一个需要理解自然语言、但任务边界清晰的子步骤。** 单纯提取项目名称、版本号和错误码，不足以说明为什么需要训练模型：固定模板、正则或现成解析器应当优先作为候选方案。更合适的迁移点不是“把文本换成 JSON”，而是**理解用户在多轮描述中表达的真实问题，按需调用只读工具补充证据，并正确更新结构化问题状态**。JSON 只是输出协议，真正要学习的是否定、纠正、指代、条件限定和新旧信息之间的关系。

**具体实例：自动修复 Bug 的 Agent 中的“问题澄清、证据查询与状态更新”模块。** 假设主流程是“输入 Bug 单 → 分析问题 → 修复代码 → 编译 → 测试 → 根据失败结果继续修改，直到验证通过或触发停止条件”。可以在接收 Bug 单及用户补充说明的位置加入这个小模块：输入是“上一轮结构化问题状态 + 本轮用户描述 + 可用工具定义”，输出分为追问、工具调用和结构化结果三类动作；工具执行后，再结合返回结果更新问题状态。它只负责把“用户到底认为哪里不对、什么情况下不对、希望改成什么样”理解清楚，再交给后续代码分析和修复模块；不承担代码根因定位、补丁生成或测试通过判断。

例如，用户围绕订单导出问题先后说了两句话：

> 第一轮：订单列表导出有问题，点了以后没反应。
>
> 第二轮：刚才说没反应不准确，文件能下下来。我先筛选出本月订单，再勾两条，导出来却把筛选出的都带上了。我只想要勾的那两条；不勾的时候还是按现在这样，把筛选结果全部导出来。

本地小模型需要完成的不是找出“订单”“导出”等关键词，而是理解以下关系：

- **纠正旧结论**：“没反应”被用户撤回，不能继续把“无法下载”当作当前故障。
- **理解指代和集合关系**：“勾的那两条”指选中的订单，“筛选出的都带上了”指实际导出了全部筛选结果，两者不是同一范围。
- **区分实际行为与预期行为**：实际是选中部分订单后仍导出全部筛选结果，预期是仅导出选中的订单。
- **理解条件与保留约束**：“不勾的时候还是按现在这样”不是另一个故障，而是要求保留未选中订单时的现有行为，不能把修复方案误解成“无论什么情况都只导出选中项”。

目标输出可以设计为：

```json
{
  "feature": "订单列表导出",
  "current_issue": {
    "condition": "已筛选订单并选中其中部分订单",
    "actual_behavior": "导出全部筛选结果",
    "expected_behavior": "仅导出选中的订单"
  },
  "preserve_behaviors": [
    {
      "condition": "未选中任何订单",
      "expected_behavior": "导出全部筛选结果"
    }
  ],
  "retracted_claims": [
    "点击导出后无反应，无法下载文件"
  ],
  "clarification_questions": []
}
```

这里的空追问列表只表示本例中的导出行为语义已明确，不代表代码修复所需的仓库、环境和复现材料已经齐全。如果用户只说“导出的不对，按我选的来”，却没有说明“选的”是筛选条件还是勾选记录，就应提出针对性追问，而不是擅自填入某一种解释。后续模块可以依据结构化结果查找导出相关代码，并分别验证“选中部分订单”和“未选中订单”两种分支；实际测试步骤和是否通过仍由后续模块及工具负责。

**进一步加入工具调用：不是只整理用户说的话，还能按需查询证据。** 假设业务系统已经提供只读查询接口，可以把它们封装为两个候选工具：`get_export_job(job_id)` 查询某次导出的状态、请求范围和结果摘要，`get_export_error(job_id)` 查询该任务记录的错误信息。前者用于核对“文件能下载，但导出的范围不对”，后者用于核对“任务失败并提示报错”。小模型需要根据用户的真实诉求选择动作和工具，而不是看到“导出有问题”就固定查询错误日志。**以下工具名称、参数和返回值均为迁移方案示例，不代表当前项目已经实现这些接口。**

接着前面的两轮对话，用户又补充：

> 我说的是测试环境刚刚那次，帮我查一下到底导出了哪些，不用查前天那个失败的任务。

此时模型既要理解用户要核对的是当前导出范围，也要排除旧失败任务，但“刚刚那次”还不能唯一确定任务。假设当前会话也没有绑定任务编号，就先输出追问，而不是编造编号或拿旧编号直接调用工具：

```json
{
  "action": "ask_user",
  "question": "请提供测试环境刚刚那次导出的任务编号。"
}
```

用户回复“这次是 exp-2048，前天那个 exp-1980 不用看”，模型应识别当前对象与被排除对象，选择查询导出记录，而不是查询旧任务的错误日志：

```json
{
  "action": "tool_call",
  "tool_name": "get_export_job",
  "arguments": {
    "job_id": "exp-2048"
  }
}
```

这段 JSON 是调用请求，不是模型自己执行查询。宿主程序负责工具白名单、参数校验、用户权限和环境绑定，再执行只读接口；示例假设测试环境已由宿主程序确认绑定，不允许模型自行扩大查询范围。假设接口能够记录请求的筛选与勾选范围，并返回如下摘要：

```json
{
  "job_id": "exp-2048",
  "status": "succeeded",
  "requested_selection_count": 2,
  "filtered_order_count": 126,
  "exported_order_count": 126,
  "export_scope": "all_filtered"
}
```

模型收到结果后，应输出供后续修复模块使用的结构化证据摘要。例如：

```json
{
  "action": "final",
  "job_id": "exp-2048",
  "observed_facts": {
    "status": "succeeded",
    "requested_selection_count": 2,
    "exported_order_count": 126,
    "export_scope": "all_filtered"
  },
  "user_requirement": "选中订单时仅导出选中项；未选中时保留导出全部筛选结果的行为",
  "assessment": "本次任务执行成功，但记录中的导出范围与用户要求不一致",
  "root_cause": null,
  "next_step": "将问题状态与查询证据交给代码分析模块"
}
```

这里要区分“任务执行成功”和“业务行为正确”，也要区分用户要求、工具事实与尚未确认的根因。查询结果可以支持“请求勾选两条、实际导出全部筛选结果”的判断，但不能据此断言具体哪一行代码有错。若接口只返回成功状态、没有导出范围，就不能生成上述范围结论；若查询为空、失败或无权限，也不能伪造结果。若实际记录与用户描述矛盾，则保留双方来源并继续澄清，不擅自覆盖任一方。

**这一段工具调用真正要训练什么？** 不是让模型记住接口名称，而是学习“何时追问、何时调用、调用哪个工具、如何从多轮对话中得到正确参数，以及如何依据工具结果继续回复”。例如“这次能下载，只是多了”与“这次下载失败了”可以对应不同工具；“不要查 exp-1980，查 exp-2048”要求正确理解否定和对象切换；已经有有效结果且没有新的查询需求时，不应无意义地重复调用。工具集合保持小而明确，编译、执行任意命令和修改代码仍由后续受控模块负责。

**与传统规则的区别，以及为什么仍然需要规则。** 这个固定例子当然也能手写规则处理，不能把“规则绝对做不了”作为模型价值的依据。要验证的区别是：换成“不是没下载，是下载多了”“只要打钩的，没打钩就照旧”等未见表达，或用户多次纠正、跨轮引用信息后，系统能否仍然得到一致的语义状态。因此，应该把规则方案作为基线，比较其与原始小模型、SFT 小模型在独立测试集上的表现，并记录维护规则的工作量。模型负责解释自然语言并提出工具调用请求，代码负责 Schema 校验、必填信息检查、工具权限与实际执行以及流程控制；已有结构化输入或确定性判断不必交给模型。**只有新表达、多轮纠正等场景的效果与维护收益经过验证，才有依据说这里值得引入小模型。**

**如何迁移本项目的训练与评测思路。** 将训练样本扩展为两类：“旧问题状态 + 用户新增描述 + 工具定义 → 追问或工具调用或结构化结果”，以及“对话与调用记录 + 工具返回 → 更新后的结构化结果或继续澄清”。重点覆盖纠正旧信息、保留未修改字段、条件分支、含糊指代、工具选择、参数缺失、对象切换，以及查询为空、失败和结果冲突。可以构造最小差异样本，例如“未勾选时导出全部”与“未勾选时禁止导出”，检验模型是否真正区分了条件对应的行为。按独立 Bug 案例划分训练集与测试集，避免同一案例的改写版本同时出现在两边；评测除 JSON/Schema 合法率外，还应关注旧信息纠正是否正确、未修改信息是否保留、条件和预期是否匹配、是否编造信息，以及应追问时有没有追问；工具调用另外评估动作选择、工具选择、参数正确性、无必要调用率，以及最终回复与工具事实的一致性。先做基模对比和 SFT，再根据错例迭代数据；DPO 仅作为有合适偏好样本时的对照，不预设收益。最后再验证量化和 CPU 推理优化能否满足部署要求，不预先保证原项目的小参数模型就能胜任这个新任务。

**面试中的讲述出发点。** 可以围绕“在自动修复 Bug 的 Agent 中，探索用领域后训练的本地小模型承接多轮问题澄清与只读证据查询，理解用户的否定、纠正和条件要求，在信息不足时追问、信息明确时调用合适工具，并将问题状态和工具证据交给后续修复模块”展开。这个切入点与本项目的多轮状态理解、结构化输出、工具调用和错误驱动训练有直接对应关系，而不是把整个自动修复能力归功于小模型。**目前仍属于迁移设想；只有实际完成新场景的数据构造、训练、评测和集成后，才能表述为已落地成果，不能直接套用原项目的实验数据。**

### 1. 简单介绍一下你的项目

> ### 💡 思路

> **最后用实测数据突出成果：** 项目不只提出方案，而是用训练前后评测和本地推理实测支撑质量、速度与资源占用的改善。质量上，0.6B 模型主集通过数从初始基模的 **2/51 提升到 40/51**，独立 holdout 达到 **21/24**；初始与最终口径经历校准，同口径的后续 SFT 迭代为 **29/51 → 40/51**。速度上，推理优化前的 SFT F16 与最终方案的代表性 TTFT 为 **6.25 秒 → 1.57 秒**，端到端时延为 **8.78 秒 → 3.73 秒**，模型体积由 **1142.7 MiB 缩小到 378.3 MiB**；延迟数据来自不同测试批次，最终值对应预热后前缀复用成功的请求。要突出的是：**后训练让 0.6B 小模型具备了承接已评测结构化任务的能力，推理优化又降低了 CPU 部署的资源与等待成本，使“用小模型完成边界明确的 Agent 子任务”成为有实验依据的可行方案。** 这些是原结构化任务的实测成果，为自动修复 Bug 场景的迁移提供依据，不等同于已测得的代码修复成功率。

> ### 🗣️ 参考答案
>
> 我这个项目研究的是，能不能用经过专项训练的本地小模型，替代 Agent 中一部分高频、任务边界明确的大模型调用。我希望把这套方案用到自动修复 Bug 的 Agent 中，承接前面的问题澄清和证据查询，而不是让小模型直接负责整个代码修复过程。

>
> 技术上主要做两件事：**一是提升质量**，通过 LoRA SFT 学习信息提取、多轮状态更新和工具调用，再根据错误补充训练数据；DPO 则作为进一步优化复杂判断的候选方法。**二是优化本地推理**，通过量化、CPU 参数调优和提示词前缀复用，降低体积和响应延迟。
>
> 已有的结构化任务实验中，0.6B 模型主集通过数从初始的 2/51 提升到 40/51，同评测口径下的后续迭代是 29/51 到 40/51；模型体积也从约 1143 MiB 压缩到约 378 MiB。代码修复场景还需要单独验证，但核心目标很明确：让本地小模型先把问题理解准确，再让后续模块完成修复。

### 2. 你的数据集是如何做的？

> ### 💡 思路
>
> **回答主线：以业务规则和人工种子样本为起点 → 扩充基础数据 → 根据失败用例补充 SFT 与 DPO 数据 → 观察评测收益确定规模 → 上线后回流真实数据。** 重点说清楚为什么选这些数据，以及新增数据是否解决了实际问题，而不是只报一个样本数量。
>
> **先确定依据，再制作基础数据。** 依据 Bug 澄清流程、输出字段和工具接口，列出模型需要处理的情况：信息完整、需要追问、用户纠正旧描述、追加保留条件、查询工具和处理查询结果。人工编写一批可靠种子样本，明确每种情况的正确动作和答案，再借鉴 Self-Instruct 的方式扩展表达和场景，经过规则检查与人工审核后进入训练集。输入包括历史问题状态、用户消息及必要工具信息，输出是追问、工具调用或更新后的问题状态。按独立 Bug 案例划分训练、验证和测试数据，同一案例的改写不跨集合。
>
> **根据失败用例补数据，不把错误答案直接当标准答案。** 训练后先在开发验证集定位错误，再构造新的同类场景。SFT 补“输入—正确输出”，例如模型遗漏了“未勾选时保持原逻辑”，就补充带保留条件的样本；结合 Contrast Sets，只改一个关键条件，如“未勾选时导出全部”与“未勾选时禁止导出”，让答案随条件变化。DPO 则固定同一输入，把完整保留要求的答案作为 chosen，把遗漏要求等典型错误作为 rejected。两类数据都围绕实际能力缺口组织，同时保留基础场景，避免补了难题却丢失旧能力。
>
> **通过效果增长决定做多少，而不是先规定必须达到某个条数。** 分批增加有价值的样本，记录数据量、任务通过率、目标错误修复和旧能力退步情况。数据增加仍有稳定收益就继续；达到阶段目标、继续增加同类数据收益有限时暂停，最后用未参与选样的测试集确认。原结构化任务中约 795 条扩展到约 1200 条的过程可作为迭代实例，但不是代码修复场景的已验证规模，也不是严格的数据量消融结论。
>
> **面试官可能追问：“只有 1200 条，真的够吗？为什么不用几万条？”** 回答分两层：先解释为什么可以从较少数据开始，再解释凭什么暂时停止扩充。我们不是训练通用编程模型，也不是让小模型掌握所有代码修复能力，而是利用基座已有的语言能力，适配 Bug 澄清、有限工具调用和状态更新这个边界明确的子任务。因此优先覆盖关键场景和决策条件，不直接照搬通用多任务 SFT 的数据规模。但范围小不等于一定容易，1200 条也不是通用标准；是否够用，要看主要场景是否达标、独立评测表现，以及补充数据后是否仍有稳定收益。可概括为：**“任务范围解释为什么可以少量起步，评测结果决定是否还要继续加。”** 原项目的数据规模只能作为方法验证依据，不能直接证明新业务也只需 1200 条。
>
> **📖 理论参考：** [第二部分 2.2：SFT 数据集做多少合适，什么时候可以停止？](#sft-data-size)，重点看“哪些条件会影响所需数据的量级”和“如何判断继续增加数据有没有价值”，其中列有任务范围、基座能力、输入多样性等判断依据及相关文献。
>
> **上线后形成真实数据回流。** 计划监控用户反复纠正、无效追问、工具或参数选择错误、结构化输出不合法等信号，筛选有代表性的案例。经授权收集、脱敏、去重和人工复核后，把正确处理过程补入 SFT 数据，把可靠的优劣对补入 DPO 候选数据，再训练并验证新旧能力后逐步发布。用户反馈或下游修复失败只是排查线索，不能直接当标签，更不能将所有失败都归因于前置小模型。该回流流程属于上线后的实施方案，不表述为已经运行。

> ### 🗣️ 参考答案
>
> 我的数据构建思路是先覆盖业务流程，再根据模型的错误逐步补充，不是一开始就追求几万条数据。
>
> 起点是 Bug 澄清规则、输出字段和工具接口。我会先人工写一批标准样本，覆盖问题描述、信息缺失、用户纠正、条件补充和证据查询，再借鉴 Self-Instruct 扩充不同表达，经过格式检查和人工审核后用于训练。同一个 Bug 的不同改写会放在同一组，避免训练和测试重复。
>
> 训练后重点看模型错在哪里。比如它能理解“勾选两条只导出两条”，却漏掉“没勾选时保持原逻辑”，SFT 就补充这类完整的正确示例，并用关键条件不同的对比样本帮助它区分。DPO 则针对同一个问题，把保留完整要求的答案和遗漏要求的错误答案组成优劣对。
>
> 数据量通过分批训练和评测决定：补数据后通过率持续提高，就继续；达到阶段目标、收益趋缓，就先停下来。不是说到了某个固定条数就一定够用。
>
> 上线后，我计划把用户纠正、错误工具调用等情况作为回流线索，经授权、脱敏和审核后补充训练数据，再做回归测试和逐步发布。这样数据集会随真实问题持续完善，而不是做完第一版就不再更新。

### 3. SFT 和 DPO 在你的项目中分别解决一些什么问题？

> ### 💡 思路
>
> **回答主线：SFT 解决基础问题，DPO 在这个基础上进一步针对疑难问题优化。** 不要先讲算法定义和损失函数，而要讲自动修复 Bug 的流程中，模型具体需要学会什么、学会以后还容易在哪里出错。
>
> **先讲 SFT：让模型具备处理 Bug 描述的基本能力。** 围绕“理解问题—补齐信息—查询证据—交给修复模块”展开：从用户描述中提取出问题功能、复现条件、实际行为和预期行为；缺少必要信息时追问；信息齐全时选择只读查询工具并填写参数；最后输出结构化问题状态。例如用户说“订单导出，勾了两条却导出全部”，模型要整理出“实际导出全部、预期仅导出选中项”，而不是只识别出“订单导出”几个关键词。这些是 SFT 要建立的基础能力。
>
> **再讲 DPO：针对基础流程已经会做、但复杂情况下仍容易出错的地方继续优化。** 延续同一个例子：用户又说“不是下载失败，文件能下载；没勾选时还是按原来导出全部”。难点就变成了同时撤回旧判断、更新当前问题，并保留不应修改的行为。可以将“正确更新故障描述且保留未勾选分支”作为较优答案，将“仍判断下载失败”或“遗漏未勾选分支”作为较差答案，训练模型更倾向于完整、准确地保留用户要求。工具查询也一样：不能看到任务状态为成功，就忽略实际导出范围错误并断言没有 Bug。
>
> **最后落到业务价值：SFT 让后续修复模块拿到可用的问题描述，DPO 的进一步优化目标是减少复杂描述中的误解、约束遗漏和证据误判，避免后续修错方向或改坏原有行为。** 这里的基础与疑难是本项目的训练分工，不是说 SFT 不能处理难题、DPO 一定能解决难题；实际提升仍以验证结果为准。

> ### 🗣️ 参考答案
>
> 我会把 SFT 和 DPO 分成“建立基础能力”和“针对剩余错误进一步优化”两个层次。这里说的是迁移到代码自动修复 Agent 的方案，小模型负责把 Bug 描述理解清楚、查询证据，再交给后面的代码修复模块。
>
> **SFT 重点解决理解和执行流程的问题。** 比如用户先说“导出没反应”，后来改口“文件能下载，但勾选两条却导出了全部；没勾选时还是导出全部”。模型需要更新旧结论，提取正确的实际行为和预期行为，同时保留未勾选时的原有逻辑。需要查记录时，还要知道缺任务编号先追问，有编号再调用正确的工具。
>
> **DPO 则用于进一步优化这些容易混淆的选择。** 比如，同一个问题下，一份答案正确保留了“没勾选时照旧”的要求，另一份却遗漏了它；或者一份在缺编号时追问，另一份编造编号。我会将这些输出构成优劣对，让模型更倾向于保留完整约束、不编造信息，并依据工具事实回答。
>
> 简单说，SFT 是先让模型会处理这类任务，DPO 是针对它已经暴露的具体错误继续优化。但这个迁移方案还没有验证 DPO 的增益，不能预设加上 DPO 就一定更好。

### 4. 你在做项目的过程中遇到了一些什么问题，怎么解决的？

> ### 💡 思路
>
> **这是一个可以从任何角度回答的问题，重点是选一个具体问题讲深，而不是罗列很多困难。** 按“发现什么异常 → 用什么数据定位 → 为什么这样调整 → 如何确认有效”组织。下面两个角度可择一展开：训练后的能力回归，或本地推理优化没有达到预期。
>
> **角度一：训练后出现回归，如何调整数据和训练参数。** 难点不是模型完全不会，而是补强一种能力后，原来会的能力反而退步。放到 Bug 澄清业务中，例如工具查询更积极了，却在缺任务编号时不再追问；或者更容易更新故障描述，却漏掉用户要求保留的旧行为。先固定评测和推理配置，逐题比较新旧模型，判断退步发生在哪里，再检查训练样本配比、学习率和训练轮数。分别验证补充边界样本、混合基础样本、降低学习率或减少训练轮数的效果，不一次改完所有参数。按业务验证结果选择 checkpoint，而不是只看 loss 或默认使用最后一轮；少量用例退步也不能直接认定为灾难性遗忘。上述 Bug 用例和参数调整是迁移后的排查方案，不将某个参数的修复效果写成已验证成果。
>
> **角度二：推理优化效果不好，如何根据测量结果逐步定位。** 不把“模型量化了”当成“响应一定更快”：先拆分 Prefill、Decode、TTFT 和端到端时延，判断时间花在哪里；再分别测试量化精度、llama.cpp 参数和提示词处理方式。量化要同时看质量与速度，必要时对比有无 imatrix、校准数据代表性及校准样本量，而不是笼统说“调整量化矫正参数”；校准改善的是量化误差，不保证所有阶段加速。推理参数要分开调 Decode 线程与 Prefill 线程、Batch/Ubatch。若瓶颈是固定长提示词，就比较压缩与前缀复用，同时检查质量退步。深度体现在能够解释“为什么某个看起来合理的优化没用，以及为什么换这个方向”。已有延迟与量化数据可引用原实验；imatrix 参数对照若未完成，只作为可验证方向。

> ### 🗣️ 参考答案一：训练后出现能力回归
>
> 我会选训练后能力回归这个问题展开。原实验里出现过修好新问题、旧用例却退步的情况，所以我不会只看总分或者训练 loss。
>
> 放到 Bug 澄清模块，比如补了工具查询样本后，模型更会调用工具了，但缺少任务编号时也可能直接发起查询；或者用户修改故障描述后，模型把原来要求保留的行为一起丢掉了。
>
> 我的处理思路是先用相同评测条件对照新旧输出，找出哪些原本答对的题变错了。如果问题集中在追问和调用的边界，就补充“缺编号先追问、有编号才查询”的对照样本，并保留基础场景，避免训练数据只偏向新能力。
>
> 参数上也不会直接加大训练量。我会固定数据，分别尝试降低学习率、减少训练轮数，并比较中间 checkpoint。如果继续训练只是 loss 更低，业务表现却下降，就选之前更稳的版本。
>
> 最后不仅看新错误有没有修复，还要确认旧能力是否保住。这里的关键经验是：训练目标不是把 loss 压到最低，而是在获得新能力的同时，维持已有业务能力。

> ### 🗣️ 参考答案二：推理优化未达到预期
>
> 我遇到的一个问题是，模型量化以后变小了，但响应并不一定更快。Bug 澄清这种前置交互需要及时反馈，所以只看模型体积或生成速度是不够的。
>
> 我先拆开测量 Prefill 和 Decode。原实验中，F16 的 Prefill 约占总时延的 65.6%，说明主要瓶颈是处理长提示词，而不是生成答案。Q8 虽然让 Decode 更快，TTFT 却没有改善，因此不能只凭生成速度选它；Q4 在体积、速度和质量之间更合适，体积减少约 66.9%，质量通过数由 60/75 变为 59/75。
>
> 接着调整 llama.cpp 参数，把 Decode 线程和 Prefill 线程分开测试，并比较 Batch、Ubatch，而不是把线程一律开到最大。针对剩下的长提示词开销，我还比较了压缩和前缀复用：激进压缩虽然快，但 holdout 从 17/24 降到 5/24，所以没有采用；前缀复用则在对应实验中把 TTFT 从 5.35 秒降到 1.57 秒，holdout 保持 17/24。
>
> 最后的方案是量化、分阶段参数调优和固定提示词复用。这个过程让我确认，推理优化要先测瓶颈，再选手段，并且每次提速都要检查质量，而不是默认量化越低、线程越多就越好。

### 5. 项目里的超参数、参数的设置有一些什么经验吗？

> ### 💡 思路
>
> **回答主线：没有做系统的训练超参数搜索，但要能讲清参数控制什么、出现什么现象时如何调整。** 本项目后训练主要围绕数据和错误迭代，不把它包装成经过精细调参才取得提升。以下组织的是理论上的选参与排查思路，用“我会如何调整”来回答，不虚构已经做过的调参实验。推理参数有实际对照，可与训练超参数区分。
>
> **先确定基本原则：** 从同类模型和训练框架的可靠配置起步，固定数据、评测与推理条件，每次主要验证一个调整方向。依据验证集上的业务表现选择参数，最终测试集不参与反复调参。对 Bug 澄清模块，重点看信息提取、保留约束、追问和工具调用是否正确，而不只是 loss 是否下降。
>
> | 参数 | 主要影响 | 遇到什么情况，如何尝试调整 |
> |---|---|---|
> | **学习率** | 每一步参数更新的幅度 | 若 loss 剧烈波动，或继续训练后旧能力明显退步，在排除数据和评测问题后，尝试降低学习率、增加适当预热；不是一出现回归就认定学习率过大 |
> | **训练轮数与 checkpoint** | 同一批数据被学习多少次 | 若训练 loss 下降、验证业务表现却变差，尝试减少轮数并选较早 checkpoint；若仍在稳定改善，再考虑延长训练，而不是默认越久越好 |
> | **LoRA rank / alpha** | 适配容量与更新缩放 | 标准 LoRA 常按 alpha/r 缩放更新。若数据覆盖充分、训练也稳定，但任务仍学不够，再尝试增大 rank；同时记录 alpha/r 的变化，避免把容量变化与缩放变化混为一谈。rank 越大不保证越好 |
> | **有效 Batch 与梯度累积** | 梯度估计的稳定性及训练资源需求 | 显存不足时先减小单卡 Batch，再用梯度累积保持目标有效 Batch。常规数据并行下，有效 Batch = 单卡 Batch × 累积步数 × 数据并行卡数；改变有效 Batch 后还要复核更新步数和学习率，不能只比较 epoch |
> | **最大序列长度** | 能否容纳完整对话、工具结果和目标答案 | Bug 多轮描述中，若关键保留条件或正确输出被截断，应先检查长度分布与截断策略，再调整长度；不能把“没有看到信息”误判为模型能力不足，长度也不宜无依据地开到最大 |
> | **DPO β** | 偏好优化与参考模型约束之间的权衡 | 在标准 DPO 对应的正则化目标中，较大 β 意味着更强的偏离惩罚，不是更强纠错。应结合较小学习率和训练轮数做少量对照，看业务收益与回归，不照搬“β 越大越好”的规则 |
>
> **推理参数补充一个真实经验即可：** llama.cpp 的 Decode 线程与 Prefill 线程应分开测试，Batch/Ubatch 要结合输入长度和内存实测。固定模型、量化和请求条件后比较 TTFT、Decode 速度及波动，不能认为线程越多、批次越大就越快。
>
> **落脚点：参数调整是验证假设，不是按症状机械套公式。** 例如模型漏掉“未勾选时保持原逻辑”，先检查输入是否被截断、训练是否覆盖这种条件，再判断是否需要调整学习率、轮数或 LoRA 容量；不能试图仅靠调参弥补缺失或错误的训练信号。

> ### 🗣️ 参考答案
>
> 这个项目在训练超参数上没有做大规模搜索，主要精力放在数据和错误迭代上。不过，我理解调参的关键不是背一组最优值，而是根据训练和验证表现判断该动哪个参数。
>
> 我会优先看学习率和训练轮数。如果训练波动比较大，或者新能力提高了、旧能力反而退步，在排除数据问题后，会尝试降低学习率。如果训练 loss 继续下降，但验证题越来越差，就减少训练轮数，保留表现更好的中间模型，而不是默认最后一轮最好。
>
> 对我们的 Bug 澄清任务，我还会特别检查最大序列长度。用户可能在后面补一句“没勾选时保持原逻辑”，如果这段被截断，调学习率也解决不了。LoRA rank 则是在数据覆盖和训练过程都没问题、模型仍然学不够时，再考虑适当增加，不是一开始越大越好。
>
> DPO 的 β 也不是越大纠错越强，它影响模型相对参考模型的约束，需要结合实际业务通过率判断。
>
> 推理侧有一个实际经验：线程不是开满就最快，要把处理提示词和逐字生成的线程分开测。总体上，我会固定其他条件、少量对照，以模型是否更准确、更稳定、更快来选参数，而不是只看 loss 或参数大小。

### 6. 你的项目为什么要使用本地模型，有一些什么意义？

> ### 💡 思路
>
> **回答主线：这是项目需求和价值的问题，直接从成本、隐私、网络依赖和可控性回答，再说明为什么选择这个业务环节做本地化。** 不需要展开训练算法，重点是说明为什么值得做，而不是为了展示技术而使用小模型。
>
> **先关联业务：** 自动修复 Bug 的 Agent 可能多次与用户澄清问题、查询证据和更新问题状态。如果这些高频步骤都调用远端大模型，会持续产生调用费用，并受网络和服务可用性影响。它们又比代码根因分析、补丁生成更容易限定任务范围，因此适合作为本地替代的切入点，而不是要求本地小模型替代整个 Agent。
>
> **讲清四个主要价值：** 一是减少这部分按次计费的远端调用；二是让 Bug 描述、内部日志等敏感信息尽量在本地处理，减少外发；三是降低模型推理对外部网络的依赖，在所需数据和工具可本地访问时支持离线使用；四是自主控制模型版本、提示词和运行环境，便于固定版本、复现问题与回滚。
>
> **性能价值要结合实测，不说本地天然更快。** 本地可以省去远端调用的网络往返，但 CPU 推理本身也可能很慢。因此项目才需要通过小参数模型、量化、参数调优和提示词复用降低延迟。比较实际收益时还要计入模型下载、内存、算力和维护成本，本地不是零成本，也不能在没有远端对照时声称一定比远端快。
>
> **最后落到项目目标：** 用后训练保证任务质量，用推理优化降低部署门槛，探索让普通 CPU 上的 0.6B 模型承接高频、边界明确的子任务。更复杂的代码理解和修复仍可交给更强模型。隐私收益也限定在本地处理环节，后续远端模块和工具是否外发数据仍需单独控制。

> ### 🗣️ 参考答案
>
> 使用本地模型主要是业务需求驱动的，不是为了本地化而本地化。
>
> 在自动修复 Bug 的 Agent 里，问题澄清、证据查询和状态更新会反复发生，但不一定每一步都需要很强的远端大模型。如果能让本地小模型承接这些边界明确的任务，就有几个价值。
>
> **第一是成本，** 可以减少高频的远端 API 调用。**第二是隐私，** Bug 描述和内部日志可能涉及敏感信息，这部分尽量在本地处理，可以减少外发。**第三是可用性，** 降低推理对外部网络和服务的依赖；如果相关工具和数据也在本地，还能支持离线使用。**第四是可控性，** 模型版本和运行环境由我们掌握，方便复现问题和回滚。
>
> 当然，本地不代表一定更快，也不是没有成本，所以项目同时做了两条优化：通过后训练提高任务质量，通过量化和推理调优降低 CPU 上的运行开销，让 0.6B 小模型具备承接这类任务的可行性。
>
> 我们希望把合适的步骤交给本地小模型，把复杂的代码分析和补丁生成留给更强模型，而不是用小模型替代整个 Agent。

### 7. 你是如何选择你的训练模型的基模的？

> ### 💡 思路
>
> **回答主线：先明确任务与部署约束 → 筛选模型系列与规模 → 做业务基线评测 → 根据后训练结果确定部署模型。** 面试官关注的不是记住多少模型名称，而是能否说清楚选择依据、替代方案和取舍。尤其要区分“选哪些模型参与训练”和“最终部署哪个模型”，这不是一次决定。
>
> **第一步，按具体任务确定能力要求。** 我们的小模型负责 Bug 澄清和证据查询，不直接生成补丁，因此不必优先追求代码生成榜单或长链路规划能力。重点看中文理解、否定与多轮纠正、状态继承、结构化输出，以及能否正确追问、选择工具和填写参数。上下文需要容纳问题历史、工具定义与结果，但不盲目追求超长上下文。
>
> **第二步，按部署条件缩小候选。** 目标是本地 CPU 运行，需要同时考虑模型权重、KV Cache 和运行时内存，以及首字和完整响应延迟。规格中选择 Qwen3 纯文本路线，依据是中文任务适配和现有微调、量化、llama.cpp 部署链路的可用性；实际比较了 0.6B、1.7B 和 4B-Instruct。这里不说“Qwen 一定比其他家族强”：其他家族的横向对照没有完成，许可证也属于需要单独核验的选型条件。
>
> **第三步，用业务实测决定训练候选，不只看公开榜单。** 原结构化任务的 51 条基模评测中，0.6B、1.7B、4B-Instruct 分别通过 **2、6、25 条**，平均总时延约为 **3.68、6.57、10.01 秒**。4B 质量更好，但当时的本地延迟较高，因此后训练以 1.7B 为主力、0.6B 为速度档对照，没有继续投入 4B。不是说 4B 不能运行，而是它不符合当时的投入与延迟取舍。
>
> **第四步，看专项训练后的质量与速度，选满足要求的较小模型。** 最终同口径复评中，0.6B 与 1.7B 主集分别为 **40/51、39/51**，holdout 均为 **21/24**；主集平均时延分别为 **5.12 秒、8.51 秒**。一条样本的差异不足以证明 0.6B 能力更强，但在质量接近时，它的速度优势支持优先进入部署优化，1.7B 则保留为备选。最终选择 0.6B 是后训练评测得出的结果，不是仅凭参数小或下载方便做出的决定。
>
> **📖 项目依据：** [开发规格中的基座选择要求](../finetune-spec.md)、[基模评测结果](../reports/baseline-m0/README.md)、[后训练候选设计](../docs/superpowers/specs/2026-07-30-phase04-training-design.md)、[最终候选复评记录](../project-log/phase-06-iteration/log.md)。上述数字来自原结构化任务，迁移到 Bug 澄清后应以独立业务评测重新验收，不直接当作代码修复成绩。

> ### 🗣️ 参考答案
>
> 我的选型分两步：先选适合训练的候选，再根据专项训练后的效果选部署模型，不是直接找参数最大或者榜单最高的模型。
>
> 首先看任务。Bug 自动修复 Agent 里，这个小模型负责问题澄清和证据查询，不负责写补丁，所以我更关注中文理解、多轮纠正、结构化输出和工具调用。同时要求本地 CPU 能运行，就必须考虑体积、内存和响应速度。
>
> 根据这些要求，项目选择了能够接入现有训练和本地部署链路的 Qwen3，实际比较了 0.6B、1.7B 和 4B。原结构化任务的基模评测中，4B 质量更好，但平均响应约十秒，因此后续主要训练 1.7B，同时用 0.6B 验证更低成本的方案。
>
> 最后的选择与最初不同：专项训练后，0.6B 和 1.7B 的主集通过数分别为 40/51 和 39/51，独立 holdout 都是 21/24，而平均响应约为 5.12 秒和 8.51 秒。质量接近时，0.6B 更快，所以最终优先优化和部署它，保留 1.7B 备选。
>
> 核心原则就是：先用任务和硬件约束筛选，再通过训练后的业务实测，选择满足质量要求、成本更低的模型。这些已有结果为 Bug 澄清场景提供选型依据，新场景仍需重新验证。

### 8. 使用本地模型意味着用户使用你们功能前要下载模型，用户可以接受吗？

> ### 💡 思路
>
> **回答主线：下载确实有成本，但可以借鉴现有产品的按需下载方式，把选择权交给用户，再通过小体积和长期使用价值降低门槛。** 不能简单说“用户一定接受”，而要讲产品上如何减少强制等待，以及为什么值得下载。
>
> **先讲已有产品怎么做。** GPT4All 官方快速入门将安装应用和下载模型分成两步：用户安装并启动应用后，通过“+ Add Model”选择模型下载，完成后加载使用。LM Studio 也提供 Discover 页面，让用户搜索模型、选择量化版本，再通过应用内下载器获取。这些主流本地模型应用提供了“应用与模型分离、用户主动选择下载”的参考，不代表所有 Agent 都这样设计，也不证明所有用户都愿意下载。
>
> **再讲我们的产品方案。** Agent 主程序与模型文件分开发放，用户选择启用本地问题澄清功能时，再确认下载推荐模型。下载前说明用途、文件大小、预计磁盘和运行内存需求；支持后台下载、进度展示、失败重试和模型删除，避免安装 Agent 时就强制拉取模型。模型未就绪时应清楚标示本地功能不可用，不静默把敏感数据转发到云端；如果提供远端替代模式，也需要用户明确选择。这些是拟采用的交互方案，不表述为已完成的安装器功能。
>
> **用实际体积说明下载门槛。** 0.6B 模型经过 Q4_K_M 量化，权重文件由 **1142.7 MiB 降至 378.3 MiB，减少约 66.9%**，不到 0.4 GiB。模型通常首次下载后即可复用，只有更新或重新安装等情况才需要再次获取，不是每次使用都下载。但 378.3 MiB 是模型权重大小，不是 Agent 整个安装包，也不是运行内存；对应实验的峰值服务内存约为 **1128 MiB**。
>
> **最后回答是否值得。** 对持续使用自动修复 Agent、重视隐私或希望减少远端调用的用户，一次性下载换取后续本地处理，有合理价值；偶尔使用或存储、网络受限的用户可以不启用。是否被接受还应通过下载完成率、启用率和用户反馈验证，而不是只凭模型小就断言没有阻力。
>
> **📖 官方做法参考：** [GPT4All：安装应用后添加和下载模型](https://docs.gpt4all.io/gpt4all_desktop/quickstart.html)；[LM Studio：在应用内查找与下载模型](https://lmstudio.ai/docs/app/basics/download-model)。

> ### 🗣️ 参考答案
>
> 我认为关键不是完全避免下载，而是不要强制所有用户一开始就下载模型。可以参考 GPT4All、LM Studio 这类产品，把应用安装和模型下载分开，让用户自己选择需要的本地模型。
>
> 我们的方案也是 Agent 主程序与模型分开发放。用户选择启用本地问题澄清功能时，再提示下载，并说明模型用途、文件大小和资源要求，下载过程可以放在后台。没有启用本地功能的用户，不需要先承担这部分下载成本。
>
> 而且我们的模型比较小：0.6B 模型经过量化，权重文件从约 1143 MiB 降到 378 MiB，缩小了约三分之二。首次下载后可以持续复用，不需要每次调用都重新下载。当然，这是模型文件大小，运行时仍要占用额外内存。
>
> 对经常使用 Agent 的用户，这是一笔一次性成本，换来后续减少远端调用、降低网络依赖，以及让敏感问题描述尽量留在本地处理。不是所有用户都必须接受，而是提供清楚的选择，让有这类需求的用户主动启用，最终再通过实际使用反馈验证接受度。

### 9. 介绍一下你这个项目的最终结果，主要的成果。

> ### 💡 思路
>
> **回答主线：质量提升 → 速度与资源优化 → Agent 集成价值。** 这题不重复讲完整实验过程，直接用关键数据说明模型从“能力不足、运行成本较高”变成“可以承接明确子任务的本地方案”。强调结果来自实际评测，而不是只列使用了哪些技术。
>
> **质量成果：证明 0.6B 小模型经过训练后能完成任务。** 原结构化任务中，主集通过数由基模 **2/51 提升至 SFT 的 40/51**，协议遵循率由 **39.2% 提升至 92.2%**，独立 holdout 通过 **21/24**。初始到最终经历了评分口径校准，同口径后续迭代为 **29/51 → 40/51**；不把这些成绩称为代码修复成功率，也不归因于尚未验证的 DPO 优化。
>
> **性能成果：展示最终方案，不拆成各项优化的流水账。** 相比 SFT 后的 F16 推理基线，最终 Q4_K_M 部署方案的模型体积由 **1142.7 MiB 降至 378.3 MiB（减少 66.9%）**，峰值服务内存由 **1688.8 MiB 降至 1128.0 MiB（减少 33.2%）**；代表性 TTFT 由 **6.25 秒降至 1.57 秒**，端到端时延由 **8.78 秒降至 3.73 秒**，Decode 由 **29.42 提升至 41.89 tokens/s**。质量代价同时报告：F16 与 Q4 的部署质量通过数为 **60/75 → 59/75**。这些代表性性能数据来自不同测试批次，最终延迟对应预热后成功复用前缀的请求，不作为冷启动或整套方案同批次对照的结果。
>
> **集成成果：落到 Agent 里的实际职责。** 集成后的目标链路是“Agent 提交用户描述与历史状态 → 本地模型返回追问、只读工具调用请求或结构化问题 → Agent 执行工具并继续流程”。强调本地模型承接前置理解与证据整理，后续模块负责代码分析、修改和验证。若已完成该链路的联调与验收，可将“本地模型接入 Agent”作为工程成果；现有文档仍将自动修复 Bug 场景列为迁移方案，未提供集成验收记录，因此下方答案保留这个事实边界，不直接写成已完成集成。
>
> **最后落脚：** 用实测质量证明“小模型能做”，用速度与资源数据证明“本地部署有可行性”，再以 Agent 联调验收证明“能够进入业务流程”。这三层证据共同支撑成果，而不是把离线通过率等同于整个 Agent 的修复成功率。

> ### 🗣️ 参考答案
>
> 这个项目的成果主要体现在质量和本地推理性能两个方面，核心是让 0.6B 小模型承接明确的 Agent 子任务有了实际数据支持。
>
> **质量上，** 原结构化任务的主集通过数从基模的 2/51 提升到 SFT 的 40/51，协议遵循率从 39.2% 提升到 92.2%，独立 holdout 达到 21/24。初始与最终评测经历了口径校准，同口径的后续迭代也从 29/51 提升到 40/51，说明专项训练确实改善了任务能力。
>
> **性能上，** 相比训练后未经推理优化的 F16 模型，最终方案体积从约 1143 MiB 降到 378 MiB，缩小约三分之二；代表性首字延迟从 6.25 秒降到 1.57 秒，完整响应从 8.78 秒降到 3.73 秒。这里是不同批次的代表性实测，最终延迟包含预热后提示词复用的收益；量化质量对照只减少了 1 条通过样本，从 60/75 变为 59/75。
>
> **应用上，** 这套本地方案面向自动修复 Agent 的问题澄清和证据查询环节：先把用户要修什么、哪些行为必须保留整理准确，再交给后续代码修复模块。已有实验验证了方法和本地运行的可行性，Bug Agent 的实际集成效果还需要单独联调验收。最终价值是用更低的本地资源开销承接适合小模型的步骤，而不是让小模型替代全部代码修复能力。
