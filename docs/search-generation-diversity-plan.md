烘焙训练数据多样性修改方案（2026-10-07）

本方案只规划实现，不启动生成、不修改 Registry、冻结评估集或现有数据。建议采用“程序分配合法意图与 Gold，模型负责自然语言表达”的方式，从源头控制条件组合，而不是继续让模型改写固定例句。

1. **现状与目标**

   当前保存了 369 条训练候选样本。按文件顺序检查最近 100 条：95 条含“可颂”，90 条含“20”；其中 49 条 hard_soft_mix 全部含可颂、20、开心果。主要原因是固定参考例句、缺少条件组合分配，以及只对原话做精确去重。现有 coverage 门槛只保证字段或能力出现过，不能发现单一组合占据大部分数据。

   保持现有 15 类场景及 1,820 条总配额。增加条件、取值、操作符、数值、单位和表达风格的分配。所有结构化内容必须先通过 Registry 和场景合同，再进入模型提示词；自然语言通过本地检查后才能入库。结构合法不等于原话与 Gold 的语义一致，仍需独立审核。

2. **Registry 作为唯一结构化事实源**

   所有候选从 `load_registry()` 返回的对象派生，不在新模块复制业务枚举。

   | 要素 | 候选来源与限制 |
   |---|---|
   | 可抽取字段 | `model_extractable_fields()`；不能选择索引内部字段如 size_g |
   | 分类值 | 对应字段的 `ValueSpec.code`；表达只选该值的 label/aliases/code |
   | 硬/软操作符 | 分别来自字段的 hard_operators / soft_operators，不跨字段套用 |
   | 数值 | 按 type、minimum、maximum、exclusive_minimum 校验；无上限的字段由配置提供有限采样池，采样池不是新的业务限制 |
   | 净含量单位 | size.units 中的 g/kg/oz，保留原话单位，不换算 |
   | 币种 | 按 price.unit_pattern 校验；可配置有限币种池及 null，不猜测未表达的币种 |
   | 排序 | search.sort_fields 中的字段及 orders；不能因为“高端”推断排序 |
   | 清除字段 | clearable_fields()，包含合同允许的 query_text/sort |

   关键边界：allergen 没有 soft_operators，过敏限制不能规划成软偏好；flavor 与 allergen 分开；具体风味不自动添加 flavor_family；纯素等声明不自动展开过敏原排除。sweetness_level/flavor_intensity 为 1–5 的整数，price 非负，size 严格大于 0。lower/higher 不凭空补阈值。

   `query_text` 和 `unmapped_terms` 是协议允许的自由文本，不是新增 Registry 枚举。前者只能保存不能安全结构化但适合全文检索的表达；后者保留用户原文，不创建未知字段或未知分类值。它们遵守现有长度、数量与场景合同。

3. **新增确定性的意图规划器**

   建议新增 `src/slot_extractor/data/generation_plan.py`。

   每个请求对应一个不可变 `IntentPlan`，包含：样本 ID、场景、当前状态、计划 Gold Patch、程序派生的断言、允许使用的取值别名、表达风格以及规范化语义签名。计划元数据只用于生成与审计，不进入 SFT 模型输入。

   先按场景构造合法候选，再按不足覆盖项优先分配，使用固定 seed 处理同优先级候选。分别统计字段、字段组合、field/value、hard/soft/operator、数值和单位的计划次数，避免只平衡字段却始终选择同一个值。

   同时规划表达风格：中文/英文/混合、问句/陈述句、简短/口语、条件前后顺序。风格不能改变条件强度，不能为凑长度增加需求。短表达是否纳入训练应单独配置，不依靠 Schema 的 minLength 代替语义质量判断。

   在模型调用前生成 `generation_plan.jsonl` 和 `plan_audit.json`；任一计划不合法或目标不可行，dry-run 即失败并报告原因。种子只能保证计划确定性，不能保证外部模型逐字复现。

4. **15 类场景的分配规则**

   | 场景 | 规划重点 |
   |---|---|
   | single_filter | 恰好一个 hard 或 soft 条件；轮换字段、合法操作符和取值；同条件内多个分类值另作明确配额 |
   | multi_filter | 2–3 个硬条件；轮换字段对/三元组；用途不推断商品形态，使用方式不推断质构 |
   | hard_soft_mix | 1–2 个硬条件与 1–2 个软偏好；从分别支持硬/软操作符的字段中选择，避免固定 application+price+flavor |
   | negation | 轮换允许 not_in/avoid 的字段，分别表达硬排除和软回避 |
   | allergy_vs_flavor | 保持安全排除/普通口味排除配额；前者只在 allergen 用硬排除，后者在 flavor，不误加另一字段 |
   | replace | 当前状态由程序构造；规划同字段不同的新值或强度；新意图整体替换旧 hard/soft，Patch 不重复其他字段 |
   | clear | 仅清除状态中实际存在的合法字段；轮换分类、数值、软偏好、排序、query_text |
   | preserve_state | 状态至少两个已有字段，仅修改其中一项；明确记录必须保留的字段，Patch 不重复它们 |
   | numeric_price | 均衡覆盖 eq/gte/lte/between、不同合法金额、零价格、显式与省略币种 |
   | numeric_size | 均衡覆盖合法操作符、g/kg/oz 和不同正数；原单位保留 |
   | relative_numeric | 只从支持对应操作符的字段规划 lower/higher/around；模糊表达不伪造精确阈值 |
   | sort | 均衡覆盖 Registry 的合法排序字段/方向；当前 Registry 共 5 种合法排序组合 |
   | query_text | 使用经过审阅的自由文本候选池；避免把已可结构化的词重复写入 query_text |
   | unmapped | 使用经过审阅的无法安全映射表达；原文保留，可配置是否同时包含一个明确合法条件 |
   | reset | 构造旧状态，明确重置，只应用新条件；旧条件不混进新 Patch |

   旧状态与 Patch 都必须独立合法；再调用现有状态合并和合同校验检查替换、清除、保留等语义。不同字段之间没有 Registry 依据的“常识兼容性”不能写成事实规则。

5. **修改模型职责和提示词**

   修改 `scenario_specs.py`：保留场景硬约束，取消每次发送同一句固定参考表达。无需通过新增静态例句列表解决锚定；提示词以当前 IntentPlan 为依据。

   修改 `generator.py`：发送程序已校验的意图、状态、Gold 和指定风格，让模型创作自然用户原话。第一阶段可保留六字段 Raw 响应，以兼容现有接口，但模型返回的状态、场景、Gold 和断言必须与计划一致；ID、标签、断言及最终 Gold 由程序持有，不接受模型改掉计划。条件数组和 values 数组比较应忽略无意义的排序差异。

   后续可让模型只返回 user_input，程序组装其余字段，减少输出格式错误；这不属于第一阶段必需改动。

   保持 Chat 普通输出，不发送强制 response_format。Schema 的 minLength 保持 1；本地质量检查、JSON 校验与失败重试继续工作。

   为每个指定条件分配合法的表面表达，明确要求出现相应别名、数值和单位。仅改变别名/语言/句式时不改变条件；重试时保留原计划，不能为了通过检查悄悄删条件、换数值或换目标字段。

6. **三层校验与重试**

   - 调用前：validate_state / validate_patch / 状态合并 / 现有数据合同校验全部通过，检查采样池是否合法。
   - 返回后：严格解析 JSON，校验六字段合同、Registry、场景、计划一致性和文本质量；检查分类值、数值、单位是否有原话依据，检查否定和硬软强度。无法用规则可靠判断的情形标记为待复核，不用简单关键词匹配宣称全部语义正确。
   - 入库前：原话去重、Frozen Eval 隔离、语义配额审计。跨场景/跨状态也不能复用同一句评估原话。

   复用现有有界重试。失败反馈列出具体计划、违例字段、合法别名和被拒绝的原话，要求按相同计划重写。保存每次失败的原始输出、原因和请求 ID 到独立诊断文件，避免下次只能根据错误摘要猜测。诊断文件不进入训练集，也不保存 API Key。

   重试次数耗尽时，保留 checkpoint 和缺失请求清单；不能放宽 Registry 或静默降低 1,820 条配额。是否跳过失败请求后继续完成其他计划，可作为后续单独的调度改动。

7. **新增多样性审计，避免“句子不同但内容一样”**

   建议新增 `diversity_audit.py`，产出 `diversity.json`。统计 scenario×field、scenario×field/value、field-pair、hard/soft/operator、数值、单位、语言与风格分布，并列出高频语义组合及对应样本 ID。

   语义签名包含场景、排序后的 hard/soft 条件及其值/单位、clear/reset/query/unmapped。多轮还需记录旧状态和变化类型，区分不同替换/保留任务；同时单独统计 Patch 签名，避免靠更换旧状态隐藏重复新意图。签名不含 ID、原话措辞或表达风格。

   精确原话重复为 0；近义原话和同语义多表达是两个不同概念，前者需检查，后者可以按配额适量保留。不能对所有相同 Gold 一律拒绝，例如 sort 60 条只有 5 个合法组合，本来就需要同条件不同表达。

   验收门槛从合法候选数量和该场景配额推导：候选数为 K、样本数为 N 时，独立平衡维度的目标次数为 floor(N/K) 或 ceil(N/K)；若维度之间存在约束不能同时满足，规划器先给出可行分配和允许偏差，而不是事后修改门槛。

   对 multi_filter / hard_soft_mix，建议试跑后确认以下初始目标：至少 10 种不同字段组合；完整语义签名唯一比例至少 80%；当某字段的某分类值有多种合法候选且配额足够时，最高占比不超过均衡目标加 10 个百分点。若候选不足则 dry-run 报不可行，禁止越过 Registry 凑组合。数值池应包含至少 8 个经验证的金额候选及多种合法区间，使预算不集中在 20；这些是数据采样目标，不是业务枚举。

   在相关场景分别报告可颂、开心果及金额 20 的占比和联合占比，审计是否仍有固定例句锚定。分母必须是相应字段/场景的样本数，不能用全数据集稀释问题。

8. **配置、版本与断点**

   使用新的训练版本 `baking-v1.1` 和配置 `configs/data/baking_search_v1_1.yaml`，继续引用现有 `data/eval/baking-v1.0/test.jsonl`。新训练版本不要求重新制作评估集；禁止从评估样本派生训练原话或从其条件分布反向定制计划。

   保留旧 369 条和旧 checkpoint 作为诊断资料，不默认混入新数据，也不删除。当前进程保持停止，方案实施后先试跑再正式生成。

   配置新增 planning/diversity 小节：表达风格权重、合法数值池、规划种子、多样性目标和有界重试参数；不在这里新增业务字段或分类值。Registry、采样配置、IntentPlan、规划器实现、提示词、质量规则、后端协议和影响生成的参数都记录 hash。API Key 不进入 manifest 或签名。

   请求 ID、计划和排程固定后再并发提交；按场景交错排程，避免开头连续几百条同一场景。checkpoint 恢复时重建并核对原计划、校验已存样本、恢复计数；不会因任务返回顺序改变计划配额。规划器或语义规则变更必须新版本，不再通过修改旧签名混合不同生成策略。

9. **建议修改范围与实施顺序**

   | 文件 | 修改 |
   |---|---|
   | 新增 data/generation_plan.py | 合法候选派生、配额分配、IntentPlan、语义签名 |
   | data/scenario_specs.py | 场景约束与固定例句分离 |
   | data/generator.py | 按计划生成原话、计划一致性校验、重试反馈和失败诊断 |
   | data/search_generation.py | 计划冻结、交错排程、版本签名、恢复计数 |
   | data/generation_quality.py | 增加原话与计划的对应检查，明确规则检查的边界 |
   | 新增 data/diversity_audit.py | 语义组合与分布集中度审计 |
   | scripts/data/generate_search_raw.py | dry-run 输出规划审计和预计分布 |
   | 新增 configs/data/baking_search_v1_1.yaml | 新版本、数值采样池、风格与多样性参数 |
   | docs/search-generation.md | 计划、重试、验收、版本说明 |

   实施顺序：先完成不调用模型的计划器与审计；再接入提示词、计划一致性和断点；然后用 mock 验证全流程；最后小样本真实试跑。真实试跑另用独立目录与独立配置，固定包含 single_filter、multi_filter、hard_soft_mix、allergy_vs_flavor 和多轮操作；试跑配额写入计划，不与正式 1,820 条 checkpoint 混用。

10. **必须通过的验证**

    - 对全部 1,820 条计划验证 Registry、状态、Patch、场景和断言；零未知字段/值、零非法操作符/单位、零越界数值。
    - 固定 seed 和配置得到相同计划及计划 hash；不同并发返回顺序不会改变分配和入库判定。
    - 调整测试 Registry 的取值、边界或操作符后，候选随 Registry 改变；非法采样配置在模型调用前失败。
    - 重点边界：allergen 禁止软偏好、flavor 不自动补父级、dietary_claim 不展开过敏原、相对数值不补阈值、币种省略保留 null、size 保留单位、clear/reset/replace/preserve 符合状态语义。
    - 模型改变计划、添加未表达条件、输出短占位符、错误否定/强度、重复原话、复用评估原话时正确重试或拒绝；重试不能改变计划。
    - 新多样性审计能拒绝一批仅换句式的“可颂+20美元+开心果”样本，又不会把合法的 5 种排序组合判为必须唯一。
    - 新版本覆盖审计和多样性审计通过后才构建 SFT；对真实试跑的自然语言/Gold 做逐条审核，正式数据分场景审核或独立复核。机器审核通过仍不视为人工审核完成。
    - 冻结评估集及 Registry 文件 hash 保持不变，运行 verify_frozen_search_eval 仍通过。

完成后，预期差异是同一场景包含不同的合法搜索意图，并针对每个意图生成多样表达。提高 temperature、换模型或增加原话重试可作为辅助实验，不能替代程序化配额与语义分布审计。
